# 播客待播列表、新集自动待播与自动续播

2026-11-07 新增，2026-11-12 修订。适用于 Web / Android / macOS / iOS 四端。本文描述目标行为与接口，实现与验证状态见文末。

每个用户只有一份有序待播列表。手动的「下一集播放」和自动的「加到最前」都只决定这一份列表里的位置，不开始播放，也不改写正在听的那一条线。相关背景见 [播客单集进度与音乐接续](podcast-progress.md)。

## 1. 概念

| 概念 | 用户看到的 | 存储 |
| :--- | :--- | :--- |
| **待播列表** | 一份有序列表。可「▶ 播放全部」、点某一集从那里顺着列表播放、移除和拖拽 | 服务端 `podcast_queue`，按用户，带版本 |
| **新集自动待播** | `ignore` / `queue_last` / `queue_next`。不显示条数微调框 | 服务端，按用户和节目 |
| **播放线** | 从节目、单集、搜索或收藏点播放，就顺着该节目；从待播列表点播放，就顺着列表 | 只在本机播放器里，不同步 |
| **自动续播** | 节目线走到头之前的只读预览 | 客户端派生，不写入队列 |
| **单集收藏** | 永久标记并保护音频 | 服务端，schema 50，按用户 |

关注只决定是否接收更新，不把历史单集写进待播。自动下载和预缓存管的是文件。「预缓存下一集」不是入队。

`podcast_inbox_baseline` 只记录关注时已经存在的单集，用来识别新的 guid。它不是稍后听，不展示，不改名。

## 2. 不变式

1. 订阅、首次抓取、OPML 导入和节目合并都不把历史单集写进待播。
2. 待播里只有用户显式加入的条目，或「新集自动待播」写出的条目。
3. 入口只有「待播列表」。「加入待播」追加到队尾；「下一集播放」按下面的位置规则插入。两个按钮都不开始播放。
4. 行内三态：`+ 待播`、`✓ 已待播`、正在播放时的 `正在播放`（禁用）。`+ 待播` 是追加，不加载当前曲目，空闲播放器的主播放按钮因此保持禁用。
5. `▶ 播放待播 (N)` 把播放线切到待播，并从列表第一项开始。点列表中的某一行，从那一行开始顺着列表播放。
6. `标为已听完` / `标为未听` 立即改进度。已听完行透明度 `0.62`，标题变灰，不显示底部进度条。
7. 单集收藏独立于关注，带 `favorite` 与 `loved`，并阻止音频清理。
8. 探索榜单有 1 小时内存缓存。
9. 自动续播不写队列。预览不参与拖拽。
10. 来源是 `manual` 或 `rule`。拖动 `rule` 行会变成 `manual`。移除即删除该行。
11. 从节目点播放不改云端队列。服务端不知道播放器正在听什么，所以不会把点播插到队首。
12. 队列和偏好按账号同步。播放线不同步。
13. `playback_states` 不接收播客条目。
14. 加入待播或收藏不隐式关注。
15. 列表顺序就是 `podcast_queue` 的显式顺序。入队时记录 `added_at`，整份 `PUT` 沿用原值；客户端缺省或传 `null` 时由服务端补齐。拖动后整份写回，来源为 `manual`。

## 2.1 两个按钮在列表中的位置

播放器里有当前单集时（暂停也算），「下一集播放」插在该集的紧后面，前提是该集已经在待播里。播放器是空的，或者当前这集不在待播里，就插到列表最前。正在听的那一集本身不再作为「下一集」插入一次。

「加入待播」永远追加到队尾，包括当前正在听的那一集。这一集已经在列表里时，再点一次不改位置，也不改来源。

两条线不会互相跳：节目线走到头就停，不掉进待播；待播走到头也停，不接该节目的后续。听完一集时，如果它同时在待播里，就从待播移除，但下一集仍跟当前这条线。进度留在单集上，要回到另一条线需要自己点。

上一集 / 下一集跟当前播放线。节目线用该节目的顺序；待播线在列表里移动。

## 3. 基线与新集分发

判定「新集」的依据是**服务端首次见到该 `(podcast_id, guid)`**，不是 `pub_date`、`podcast_episodes.created_at` 或 `podcast_follows.created_at` 之间的日期比较。RSS 首次抓取会一次性写入 feed 中全部历史单集，用时间比较会把它们全部误判为新集。

- 用户首次关注某节目时，把当时已存在的全部单集记为基线，按 `(user_id, podcast_id)` 保存。基线内的集不触发任何规则。
- 后续抓取中新插入的 guid 才触发分发：遍历该节目的关注者，按各自「新集自动待播」写入这份队列。分发不开始播放，也不改当前这条播放线。
- 分发在服务端抓取事务内完成，只处理成功插入的集；抓取部分失败时不重放。
- 老数据迁移必须为所有现存 `(user_id, podcast_id)` 补写基线完成标记，避免升级后首次刷新灌入历史单集。
- 取关再关注不重置基线，进度与偏好保留。节目合并去重时基线随保留节目迁移。

## 4. 新集自动待播设置

向用户呈现精简的三选项选择器：

| 值 | 行为 | 适用 |
| :--- | :--- | :--- |
| `ignore` | 不入队 | 连载的初始默认 |
| `queue_last` | 这一批按发布时间从旧到新追加到队尾 | 每期都听（默认） |
| `queue_next` | 这一批按发布时间从新到旧插到列表最前，最新的一集在最前 | 想先听到最新一集 |

同一批里的顺序只看发布时间（解析不了再用集号和原顺序）。`queue_next` 是列表位置，不是「当前正在听的那集之后」。服务端不知道播放器。

- 新写入的 `inbox` 返回 422。库里旧的 `inbox` 在 schema 52 迁成 `queue_last`。读到旧值时客户端也按 `queue_last` 显示，并且不再把 `inbox` 写回去。
- `auto_limit` 仍留在偏好里，避免旧请求体缺字段。分发不再用它做单节目上限，界面不显示微调框。
- 全局上限 5000。自动入队若会超过上限，这一批整批不加入，并在 `GET /podcasts/queue` 的 `notice` 里写 `queue_full`。不把溢出改放到别处。用户成功 `PUT` 队列后 `notice` 清空。
- RSS `itunes:type` 为 `serial` 时，若该用户还没有这条节目的偏好，初始写成 `ignore`、从旧到新、跳过已听完、自动续播开。已有偏好不改写。这个标签经常不准，用户可以改。`episodic` 仍用账号默认，通常是 `queue_last`。
- 「从第一期开始追更」把节目顺序改成从旧到新并跳到最早未听，不把整季倒进待播。
- 设置存在服务端。分发发生在抓取事务里。

## 5. 自动续播规则

客户端纯函数 `nextEpisode(current, detail, progress, preference)`，输入为当前集、节目单集列表、每集进度与偏好，输出下一集或停止。四端共用同一组测试向量。

- 以当前集所属节目为边界，不跨节目合并。
- 排序方向为跟随列表 / 从旧到新 / 从新到旧 / 关闭，默认跟随；默认跳过已听完。
- 只在播放线是「节目」时接管，待播里有没有条目都不影响。播放线是「待播」时，下一集是列表里的下一项，播完列表就停。
- 关闭自动续播只停止节目线的自动前进和预览。待播列表还在。
- 不沿用音乐的随机或循环模式。
- 预览项可「加入待播」转为真实条目；本次主动移除的预览项不回插。
- 「从第一期开始追更」把续播锚点设到最早未听集并按从旧到新播放，不向队列写入整批条目。

## 6. API

需要登录，按当前认证用户隔离，沿用既有 Web CSRF 或 Android 认证方式。路径相对 `/api/v1`。

没有 `/podcasts/inbox`。调用它按未注册路由处理。

`GET /podcasts/queue` 返回 `{version, device_id, items:[{episode_id, origin, added_at}], updated_at, notice}`。`notice` 为空字符串，或 `queue_full`。`added_at` 为服务端入队时间，历史条目缺失时退回该队列的 `updated_at`。

`PUT /podcasts/queue` 请求 `{version, device_id, items:[{episode_id, origin, added_at?}]}`，整份 CAS 替换。已存在的 `added_at` 保留，新条目由服务端补写，`added_at: null` 与缺省同等。成功响应带 `notice: ""`。版本落后返回 409 `{"detail":{"code":"podcast_queue_conflict","current":{...}}}`。条目不是可访问单集返回 422。冲突后客户端保留本机队列并给出三个动作：用服务器版本、用本机覆盖、仅保留本机且暂不覆盖。不静默覆盖。

`GET /podcasts/queue/preferences` 与 `PUT /podcasts/queue/preferences` 读写 `{default_action, auto_limit, auto_continue, shows:{[podcast_id]:{action, auto_limit, order, skip_completed, auto_continue}}}`，标量后写覆盖，`shows` 按提交映射同步。客户端读取续播偏好的优先级统一为：**节目单独设置 → 账号默认值 → 网络不可用时使用对应账号的本地缓存**。

`PUT /podcasts/episodes/{episode_id}/favorite` 请求 `{favorite: bool}` 或 `{loved: bool}`（缺省默认为 true），返回 `{episode_id, favorite: bool, loved: bool}`。单集不存在返回 404。收藏后冻结底层音频零引用计时；取消收藏且无其他引用时恢复零引用计时。

`GET /podcasts/favorites/ids` 返回当前用户收藏的全部单集 ID 列表 `{ids: [str]}`。

`GET /podcasts/favorites` 返回当前用户收藏的全部单集详细列表（附带节目元数据、收听进度与下载状态）。

`GET /podcasts/discover` 与排行榜查询具备服务端与客户端 1 小时 TTL 缓存，支持空闲时静默预加载。

队列条目只允许本用户有权访问的节目单集 ID；服务端校验节目授权，不信任客户端提交的排序外字段。所有写操作不产生音乐收听统计、推荐反馈或 Last.fm 记录。

## 7. 边界状态

- 待播列表为空：提示「待播列表为空」，说明加入待播或关注节目更新后会出现在这里，给出浏览节目入口。
- 队列为空：区分「自动续播开启，播完会接下一集」与「已关闭，播完即停」。
- 单集收藏列表为空：提示「暂无收藏单集」，说明在单集菜单或详情中点击「单集收藏」可快速标记并保留音频。
- 加载：队列同步、节目详情读取各有布局匹配的骨架，不阻塞当前播放；探索榜单优先使用 1 小时内存缓存，避免白屏或转圈。
- 错误：同步失败保留本机队列并平静说明「暂时无法同步，本机播放不受影响」及重试入口；单集失效说明原因与下一步。
- 权限不足：普通账号按服务端校验，不显示无响应的管理入口。
- 超限：用户手动加入超过 5000 时说明上限，不截断写入。自动入队会超过 5000 时整批不加入，列表上显示队列已满、这次的新集没有加入，删掉一些后再刷新节目。

## 8. 验收场景

1. 关注一个已有数百集的节目，待播列表为空，节目页可浏览全部历史集。
2. 之后 RSS 出现新集：`queue_last` 把这一批从旧到新加到队尾；`queue_next` 把这一批从新到旧加到最前；`ignore` 不入队。正在听的内容不因此切换。旧值 `inbox` 不再接受。
3. 单集列表行内三态快速切换：点击 `+ 待播` 变为 `✓ 已待播` 且加入待播列表；再次点击 `✓ 已待播` 从待播中移出恢复为 `+ 待播`；正在播放的单集按钮变为 `正在播放` 且禁用点击。
4. 头部快捷操作：存在待播单集时，点击 `▶ 播放待播 (N)` 立即顺次起播待播单集。
5. 单集菜单点击 `标为已听完`，进度更新至 100% 并显示 `✓ 已听完` 状态标签，整行置灰降低透明度，底部进度条隐藏；点击 `标为未听` 进度重置为 0，恢复正常行样式。
6. 单集菜单或单集详情中点击 `单集收藏`，单集标记为已收藏；节目详情单集工具栏选择 `已收藏` 过滤标签，只展示被收藏的单集。
7. 收藏的单集音频在服务端受到防清理保护：即使零引用且未听完，自动或手动资源清理也不会删除其音频文件。
8. 探索榜单在 1 小时内重复打开无需重新拉取网络，秒开展示无转圈。
9. 手机排好队列，Mac 打开顺序一致；两台设备并发修改不丢数据，版本冲突可见。
10. 从节目点播放不改队列，播完后仍顺着该节目，即使待播非空。该集若也在待播里，播完后从待播移除。从待播点播放则顺着列表，列表走完就停。
11. 队列里只出现显式条目，自动续播不写入队列。节目线关闭自动续播后，这一集播完即停。
12. 加入待播不产生关注，也不开始播放。播客队列不污染音乐接续快照。音乐队列在播放器为空且选择「下一首播放」时仍会开始播放，这条不适用于播客。
13. 拖动或上下移动后顺序立即生效，刷新或换设备后保持，不按加入时间重排。
14. 四端空、加载、错误、权限不足状态与窄屏、浅深主题逐张核对。
