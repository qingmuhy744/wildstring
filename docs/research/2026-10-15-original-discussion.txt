我建议你把它定位成“面向中文曲库的自托管音乐服务器＋全平台播放器”，而不是“接几个音乐平台接口的聚合播放器”。 两者看起来相似，但数据来源、架构和商业化风险差别很大。

在“用户自己拥有音乐文件，部署到 NAS／服务器，再用客户端听歌”这个前提下，我的主推荐是：

客户端用 Flutter；服务端兼容 OpenSubsonic；歌曲信息采用本地标签优先的多源匹配；歌词做成独立、可替换的数据源模块。

初期可以用 Navidrome 验证客户端和中文信息匹配，再决定哪些服务端能力必须自研。

下面的能力信息来自当前官方文档和项目仓库。我没有拿你的实际曲库做批量测试，因此不会给出“中文歌词覆盖率 95%”之类未经验证的数字。

一、歌曲信息：不要押注一个“万能音乐 API”
你需要的歌曲信息，其实应该拆成三层：

信息层	典型字段	推荐处理方式
文件自身的信息	编码、时长、采样率、码率、内嵌标签、封面	本地扫描，作为基础
作品与发行信息	歌手、专辑、发行日期、曲目编号、版本、参与人员	本地标签＋外部数据库匹配
展示增强信息	歌手头像、简介、专辑介绍、风格、相似歌手	可选的数据源，不影响基本播放
我的建议是：第一层必须完全离线可用，第二层允许人工纠正，第三层可以缺失。 不要让某个在线接口挂了，整个音乐库就变得不可用。

1. 本地标签应该是第一来源
优先读 MP3、FLAC、M4A 等文件中的标签、封面和歌词，同时识别同目录的封面及歌词文件。TagLib 是可以评估的标签读写库，官方提供多种音频格式支持，许可证为 LGPL／MPL 双许可，具体集成仍需按所选许可处理。

我建议优先级这样设计：

用户手动锁定的信息 ＞ 用户指定的本地文件／标签 ＞ 自动匹配结果 ＞ 从文件名猜测。

关键不是“自动刮削能力有多强”，而是不能把用户已经整理好的曲库刮坏。默认把修正保存在数据库里，只有用户明确选择“写回文件”时才修改原文件。

2. 外部歌曲信息来源怎么选
来源	能解决什么	我的建议与边界
MusicBrainz	歌手、录音、专辑发行版本、曲目关系、稳定标识	适合做结构化信息骨架，但不能直接推断你的中文曲库命中率。核心数据是 CC0，补充数据并非全部同一许可。
AcoustID＋Chromaprint	文件名、标签不可靠时，通过音频指纹找候选录音	适合疑难匹配，不是歌词库。其公开服务的免费使用有非商业限制，商业使用需要另行安排。
国内音乐平台数据	中文歌曲候选、平台歌曲 ID，以及平台能够提供的其他字段	值得评估，但必须区分正式合作接口和社区适配。QQ 音乐有官方开发合作渠道，不能据此认定存在任意调用、可自由再分发的歌词数据库 API。
Last.fm	歌手、专辑补充信息及播放记录生态	适合增强，不建议作为中文核心信息唯一来源；标准 API 条款与商业用途需要分别核实。
TheAudioDB	社区维护的艺人、专辑资料和图片	可作为补充。其条款对免费开发、正式发布应用有区别，不宜理解为“免费 Key 可以直接上架商用”。
还有一个容易忽略的点：MusicBrainz 数据能否使用、其公共 API 能怎样使用、封面能否再分发，是三个问题。 公共 API 有限速要求，官方要求客户端通常不超过每秒一次请求；封面也不属于 MusicBrainz 的 CC0 核心数据库。

所以，我不会设计成“每个用户一扫描曲库，就逐首毫无限制地调用 MusicBrainz”。

3. 中文曲库的难点主要在“匹配”，不只是数据源
建议把中文搜索和歌曲身份识别分开做。

搜索层可以支持简繁体、全半角、拼音、歌手别名、英文名、标点归一化；展示层保留用户原始名称和正式名称，不要为了搜索方便把全部内容改成简体或拼音。

匹配层至少联合使用：

歌名＋歌手＋专辑＋时长＋版本标记＋已有外部 ID

其中最重要的是区分：

同名不同歌手，原唱与翻唱。
录音室版、现场版、伴奏版、混音版。
同一录音出现在原专辑、精选集、重发行版本中。
例如，音频指纹找到了同一段录音，也不代表已经找到了用户手里那一版专辑。 MusicBrainz 本身就区分录音和发行，并允许不同发行使用相同录音；你的模型也应该保留这种区别。

我建议自动匹配分成三个结果：高置信度自动采用、存在歧义等待确认、未找到保留原信息。不要为了提高“匹配成功率”，把错误结果自动塞进去。

二、歌词方案：本地优先，多源补充，商业授权单独处理
歌词比歌名、歌手这些事实字段更复杂，既涉及版本和时间轴，也涉及作品使用授权。建议你把“获得歌词”“判断是否匹配”“渲染歌词”做成三个独立模块。

1. 本地歌词：必须做，而且要做到最好
建议第一版就支持：

同名 .lrc、纯文本歌词、文件内嵌歌词，以及用户手动导入／替换。

逐字歌词则逐步支持增强 LRC、TTML 等格式。LDDC 已经提供本地歌曲匹配、多种歌词格式转换及内嵌／导出功能，适合研究实际文件兼容问题。

对于自托管产品，我认为本地歌词有很高的产品价值：用户整理一次，后续不必依赖某个在线源是否还能访问。

产品上最好支持“重新匹配”“选择其他版本”“调整时间偏移”“锁定当前歌词”“导出歌词”，而不是只显示一个无法纠正的自动结果。

2. LRCLIB：适合作为基础在线歌词源
LRCLIB 提供面向程序的歌词 API，可以按歌名、歌手、专辑、时长等信息查询，返回纯文本和同步歌词等数据，不要求先申请 API Key。它的服务端也公开了源码和自托管方式。

我的定位是：值得接入的基础来源，但不能未经测试就当作中文歌词唯一来源。

尤其要注意：

LRCLIB 服务端代码使用 MIT 许可，不等于库中所有歌词的内容版权都自动变成 MIT。 软件许可证和歌词展示、缓存、分发授权需要分开判断。

因此，自用原型与面向客户提供统一歌词服务，应该采用不同的上线审核标准。

3. 中文歌词：重点研究 LDDC，但不要把它当作商业数据供应商
这次调研里，LDDC 是很值得你看的中文歌词项目。它支持 QQ 音乐、酷狗、网易云音乐、LRCLIB 等来源，涉及逐字歌词、翻译、罗马音、本地歌曲自动匹配和多格式转换，许可证为 GPLv3。

它对你的价值主要是：

研究中文候选匹配、歌词格式处理、时间轴归一化，以及本地曲库的工作流程。

但要区分三件事：

有实现代码，不代表上游接口长期稳定；
能拿到歌词，不代表取得商业展示授权；
项目开源，不代表可以不看许可就复制进闭源产品。

另一个项目 Music Tag Web 更偏曲库整理，包含多源标签、封面、歌词处理和 NAS 部署等能力。但它的许可说明有一个明显问题：仓库标识 GPLv3，README 又附加了禁止商业用途的条款。商业复用前需要找作者澄清，不能直接按普通 GPL 项目处理。

另外，旧教程常引用的 Binaryify/NeteaseCloudMusicApi 原仓已经归档。延续分支不代表都不可用，但我不会让一个未经维护状况验证的非官方适配成为产品的唯一核心依赖。

4. 正式商业歌词：考虑授权供应商，而不是只考虑“付费接口”
LyricFind 是可以询价的正规候选，其官方产品包括静态、逐行和逐字歌词展示。

但针对你的产品，需要拿到明确答复的不是“有没有歌词 API”，而是：

中国大陆授权范围、中文曲库覆盖、用户自有音乐文件的匹配场景、NAS 自托管分发方式、离线缓存、逐字歌词与翻译权限，以及计费和最低费用。

这些我没有找到足以替代商务合同的公开答案，不能给你编一个价格或保证覆盖。

我的建议是：原型阶段把授权供应商接口预留出来，正式收费并统一提供歌词服务之前，再完成授权与成本验证。

5. 歌词内部格式不要直接绑定某一家平台
建议内部统一成这样的概念模型，而不是把上游返回的字符串原样扔给客户端：

LyricsDocument
  来源、版本、匹配依据
  原文 / 翻译 / 发音标注等独立轨道
  语言
  行起止时间
  字 / 词 / 音节起止时间
  全局时间偏移
  用户是否手动锁定
特别注意，翻译、罗马音和原文不一定是一行对一行、一个词对一个词。当前 OpenSubsonic 的结构化歌词文档也明确要求把不同类型轨道视作独立层。

客户端以实际播放时钟驱动歌词，服务端负责提供时间数据。没有准确逐字时间时，就显示逐行歌词，不要把一行的时长平均分给每个字，冒充准确逐字歌词。

三、客户端：我最推荐 Flutter，但要接受音频与系统功能分平台适配
1. 几条路线的选择
下表中的优先级是我针对你这个五端音乐产品的工程判断，不是框架性能排名。

路线	五端情况与代价	我的判断
Flutter / Dart	官方支持 Android、iOS、Windows、macOS、Linux；UI 和大部分业务可以共享，音频及系统集成仍需适配。
小团队首选
Tauri 2＋React / Vue	支持桌面和移动端；移动原生插件可用 Swift、Kotlin 等实现。
已经很熟前端、愿意维护原生音频插件时值得选
Kotlin Multiplatform＋Compose Multiplatform	移动和桌面均可覆盖，iOS 已进入稳定阶段。
团队重 Kotlin／Android 时是很好的备选
React Native＋各桌面实现	Windows、macOS、Linux 属于不同的扩展平台项目，不是统一的一套第一方五端支持。
手机优先可以考虑；你明确要求 Linux，我会降低优先级
桌面单独采用 Electron 是另一条现实路线，Feishin 就是可研究的 React／Electron 音乐客户端。但它更适合作为“桌面一套、移动另一套”的方案，而不是你这次的一套五端方案。

2. 一个和你很贴近的参考：音流
音流已经使用 Flutter 开发 NAS 音乐播放器，支持连接 Subsonic、Navidrome、Emby、Jellyfin 等服务。其官方介绍列出 Android、iOS、macOS、Windows；这份介绍没有列 Linux，所以不能把它当成已经验证了你全部五端要求的证据。

它公开的开发笔记很有参考价值，涉及 media_kit、audio_service、Windows 媒体控制、桌面窗口以及 Flutter 与 Rust 桥接。这比只看一个“Flutter 音乐播放器 Demo”更接近你实际会遇到的问题。

我的判断是：Flutter 做这类产品是现实路线，不需要为了“音乐播放器”而先写五套原生 UI。

但也不要把“共享 UI”理解为手机页面直接拉宽。建议共享组件和业务逻辑，分别设计移动布局和桌面布局；桌面需要键盘、右键、多选、拖拽、托盘等交互。

3. 音频引擎：建议留两条实现路线
路线 A：移动及 Apple 平台优先使用原生后端，Windows／Linux 使用其他后端
可以从下面的组合开始验证：

平台	播放候选	后台与系统媒体控制候选
Android、iOS、macOS	just_audio	audio_service，配合平台音频会话配置
Windows	just_audio_media_kit 或直接封装 media_kit	SMTC 集成，例如评估 smtc_windows
Linux	just_audio_media_kit 或直接封装 media_kit	MPRIS 集成，例如评估 audio_service_mpris
just_audio 自身的主要平台实现覆盖 Android、iOS、macOS、Web，Windows／Linux 需要额外实现；audio_service 的平台覆盖也不能简单理解为五端完全一致。

路线 B：统一使用 media_kit
media_kit 提供跨平台音视频播放能力；音流的开发笔记也记录了采用它替代原有播放方案的经验。对于你这种可能面对多种本地音频格式的产品，它值得和路线 A 同时做小规模验证。

我不会只凭文档断言“统一 media_kit 一定更省电”或“原生后端一定更稳定”。这两个判断都需要真实设备测试。

无论选哪条路线，都建议自己定义：

PlaybackEngine       播放、暂停、跳转、队列、速度等
MediaSessionBridge   锁屏、耳机、系统媒体键
DownloadManager      离线下载、恢复、清理
LibraryRepository    服务端与本地曲库访问
LyricsRenderer       歌词展示
业务层不要直接依赖播放器插件的所有细节。 某个平台后端有问题时，应该只换适配层，而不是改一遍全应用。

4. 一个必须提前验证的问题：无缝播放
just_audio_media_kit 当前文档把基于 prefetchPlaylist 的无缝播放明确标成高度实验性，默认关闭。

这不代表 Flutter 做不了，而是说明：

“支持播放列表”不等于“连续专辑、现场专辑在五个平台都没有接缝”。

同样，后台播放也不是一个 UI 开关。Android 官方推荐通过服务承载播放器和媒体会话；Apple 平台需要正确配置音频会话及后台播放能力。

我建议先测试锁屏连续播放、耳机切歌、来电打断、蓝牙断连、Wi-Fi／蜂窝切换、服务端短暂离线和应用重启恢复，再投入大量时间做歌词动画。

5. 离线缓存要当成正式功能设计
不要把播放器插件的实验性缓存接口直接等同于完整下载系统。just_audio 文档也将其锁定缓存音源标为实验性。

建议离线模块有自己的任务数据库、临时文件、完成校验、版本标识和空间清理规则。歌曲换了文件或改了转码质量后，旧缓存不能继续被误认为是当前版本。

另外，应明确区分“原始无损下载”和“节省空间下载”。FLAC 转成 AAC／Opus 后，就不能继续标成原始无损。

四、服务端：建议兼容 OpenSubsonic，不要全部私有化
1. OpenSubsonic 解决的是互通，不是要求你复制现有产品
OpenSubsonic 是在 Subsonic 生态上发展的兼容协议，通过扩展机制增加能力。它适合作为曲库浏览、搜索、播放、歌单等基础接口的兼容层。

我的建议是：

基础音乐功能兼容 OpenSubsonic；曲库整理、匹配候选审核、来源管理、任务进度等功能使用自己的 API。

这样，自研客户端不必被旧接口束缚，同时服务器也不至于只能被你自己的客户端使用。

还有个和中文歌词特别相关的新细节：当前 songLyrics v2 已定义 enhanced=true，支持逐字／逐音节时间、翻译与发音等轨道。 不应再按“OpenSubsonic 只有普通逐行歌词”来设计。实际使用仍需要探测双方支持的扩展版本，并给旧客户端降级。

2. 初期用 Navidrome 能节省什么
Navidrome 可以作为客户端原型的测试后端；它当前的扩展体系还包括元数据代理、歌词来源和播放记录等插件能力。

因此，你不必第一天同时完成：

服务端扫描器、数据库、协议、中文匹配系统，以及五端播放器。

更务实的方式是：先用现有服务器验证客户端和数据源模块。当确实发现曲库模型、编辑流程或产品形态受限时，再实现独立服务端。

但不要先假定一个插件就能修改 Navidrome 的所有歌曲核心字段。批量标签整理和你的业务数据，可能仍适合放在独立的预处理模块中。

3. 自研服务端，我会从模块化单体开始
我的起步选择会是：

Go＋SQLite＋FFmpeg＋本地文件目录，优先提供 Docker 的 amd64／arm64 部署。

这是针对自托管分发的工程取舍，不是说其他语言不行。若你使用 Python 开发明显更快，先用 FastAPI 也合理；不建议为了语言选型拖住产品验证。

第一版没必要因为“以后可能有很多客户”，就默认要求每个用户部署 PostgreSQL、Redis、消息队列和一组微服务。

内部建议至少分开：

扫描与标签读取、曲库模型、外部信息匹配、歌词管理、串流与转码、用户和播放状态。

数据模型则不要只有一张 songs 表。建议区分：

录音 Recording、发行版本 Release、发行中的曲目 ReleaseTrack、实际文件 MediaFile，以及外部平台 ID 映射。

你的内部主键应该属于你自己的系统，而不是直接使用网易云或 QQ 音乐歌曲 ID。

4. 外部来源必须能够失败
我建议每个 Provider 都提供统一结果结构，并记录来源、抓取时间、匹配依据和错误类型。至少区分：

确定没有结果、请求超时、需要认证、触发限流、返回格式变化。

“暂时请求失败”不能被缓存成“这首歌永远没有歌词”。

调用策略也应做到缓存、退避、限速和单源禁用。不要让全部客户共用你维护的一份私人平台 Cookie，更不要把一个在线源的状态和本地音乐播放绑在一起。

串流侧，原文件直传要正确处理 HTTP Range 及媒体响应头；播放器文档明确提示这些会影响时长识别和跳转。转码流的跳转则应单独设计，不能简单冒充完整静态文件。

五、哪些现有项目最值得看，哪些只能参考不能直接搬
我会按下面的目的研究，而不是找一个仓库直接改名字：

项目	最值得研究的部分
Navidrome	服务端曲库、协议兼容、扫描与插件边界。
音流	中文用户的 NAS 客户端形态，以及 Flutter 音频和系统集成经验。
Finamp	Flutter 移动音乐客户端、离线播放流程；它是 Jellyfin 客户端，不是现成的 OpenSubsonic 客户端。
Feishin	桌面曲库浏览、播放器界面以及 Navidrome／Jellyfin／OpenSubsonic 客户端设计。
LDDC	中文歌词匹配、逐字时间与格式转换。
AMLL	Apple Music 风格歌词渲染；它偏 Web／React／Vue，许可证为 AGPLv3，不是可直接塞进 Flutter 的原生组件，也不是歌词授权来源。
这里的“参考”和“复用代码”要分开。GPL 并不禁止商业销售，但商业销售也不等于可以闭源复用 GPL 代码而不履行义务。

音频依赖同样要检查到二进制层：Flutter 包标为 MIT，并不代表其打包进去的所有原生库也是 MIT；FFmpeg 的许可会受到实际编译选项和组件影响。

六、我建议的落地顺序
第一阶段：先证明“歌能匹配对、五端能稳定播放”
准备一个你有权使用的 300～500 首测试曲库，覆盖国语、粤语、繁体标签、独立音乐、日韩／ACG、现场版、重名歌曲和多个发行版本。

对信息来源分别统计：正确匹配率、错误匹配率、同步歌词可用率、逐字歌词可用率、人工修正成本，以及国内网络下的请求失败情况。

同时做最小 Flutter 播放器，在五端验证串流、跳转、后台控制和离线文件。数据覆盖和播放稳定性，都比第一版界面是否漂亮更值得先验证。

第二阶段：完成真正可用的最小产品
我建议范围收敛到：

一个服务器连接、本地曲库扫描、歌手／专辑／文件夹浏览、搜索、歌单、原文件播放、必要转码、离线下载、逐行歌词和手动修正。

暂时不要把整轨 CUE、DSD、独占输出、复杂推荐、CarPlay／Android Auto、多平台歌单同步和所有网盘接入一起做进去。它们可以作为后续独立能力，而不是第一版完成的前提。

第三阶段：补中文差异化和正式发行条件
再重点完善中文别名搜索、歌词版本选择、翻译／发音轨道、逐字渲染、重复文件处理，以及跨设备播放状态。

商业发行时，应分别审查代码许可、API 服务条款、歌词／图片内容授权和应用商店要求。Apple 对未经授权从第三方来源下载、保存或转换媒体有明确限制；这和用户下载自己服务器上的合法文件不是同一个场景。面向中国大陆发布时，还应检查适用的 App 备案及商店资料要求。

最终建议
客户端选 Flutter，是我对你这组五端要求最明确的推荐。 音频层通过自己的接口封装，验证 just_audio 原生后端组合与 media_kit 路线，而不是把整个产品押在某一个插件上。

歌曲信息选“本地标签＋MusicBrainz＋可插拔中文来源”，歌词选“本地歌词＋LRCLIB＋可替换的中文／授权来源”。 不把未经授权的抓取接口当成商业产品的永久基础设施。

服务端坚持 OpenSubsonic 兼容，初期可以借 Navidrome 验证，自研时从模块化单体做起。 这个产品真正值得投入的差异化，是中文歌曲识别得准、歌词能纠正、曲库不被乱改，以及五端在锁屏和断网之后仍然好用。

我现在要给这个项目立项了，给我一个合适的名字吧。
