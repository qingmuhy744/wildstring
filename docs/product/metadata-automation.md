## 3. 贡献者：身份、角色和展示署名分别保存

### 3.1 推荐模型

- **创作人/艺人身份**：稳定 ID、显示名、人物或团体类型、别名、外部来源 ID。乐队可以作为独立艺人，不根据成员名单自动给每首歌增加成员署名。
- **歌曲贡献关系**：曲目 ID、创作人 ID、角色、署名顺序、当时署名、来源。一个人可以兼任多个角色，一个角色可以对应多人。
- **专辑署名**：独立保存专辑艺人及顺序，用于专辑归属与归档，不取全专辑贡献者的简单并集。
- **展示文字**：保留 `A feat. B` 等署名表达；搜索和点击使用 A、B 的独立身份。

例如一首歌可以同时记录：演唱 A、B；作词 C；作曲 A；编曲 D。点击 C 能看到其作词作品，不能把这些作品默认归为 C 演唱。

贡献者页面提供“全部参与 / 演唱 / 作词 / 作曲 / 编曲”筛选。“全部参与”的歌曲数按曲目去重，角色关系分别保留；不能因同一人兼任三种角色把一首歌计为三首。

主要艺人署名与具体贡献角色也要区分：器乐曲只有 `ARTIST` 时可保留主要艺人，但不凭该字段虚构“演唱”角色。首批界面聚焦四类角色，原始的演奏、制作等其他角色信息仍保留，数据模型允许后续扩展。

### 3.2 自动解析规则

1. 优先使用文件中的明确多值标签，保留顺序和原始观测值。
2. 同时存在独立名单与展示署名时，分别保存；名单内部不再按标点二次拆分。
3. 只有单串 `A/B`、`A & B`、`A feat. B` 时生成拆分候选，结合已知身份和来源核对；首批不把分隔符规则全量自动应用到旧库。
4. 自动清理首尾空白、重复的同一身份关系；繁简、译名、艺名和同名人物先作为匹配线索。身份合并需要可靠外部 ID 或人工确认，保留原署名。
5. 缺失词曲编字段保留未知；不能凭歌名或模型印象补成事实。翻唱者、原唱者和词曲作者分别处理，编曲信息按具体录音版本核对。

展示署名与独立艺人的区分参考 [Navidrome 多艺人标签](https://www.navidrome.org/docs/usage/library/tagging/)；署名顺序、名称与连接词参考 [MusicBrainz Artist Credits](https://musicbrainz.org/doc/Artist_Credits)。以上自动应用边界是本项目的推荐策略。

## 4. 专辑：先确认归属，再确定托管路径

| 场景 | 推荐专辑署名 | 歌曲如何记录 |
| --- | --- | --- |
| A 的专辑包含与 B 合唱的一首歌 | A | 合唱曲保留 A、B 的演唱关系，专辑其余歌曲不增加 B |
| A、B 联名专辑 | A、B | 每首按实际参与者记录，不强制全部歌曲都为两人演唱 |
| 群星合辑 | 群星，标记为合辑 | 每首保留实际演唱与词曲编，群星不代替个人贡献者 |
| 影视原声 | 按具体发行署名及类型核对 | 不因为多人参与就一律改为群星 |
| C 为整张专辑编曲 | 保留原专辑署名 | 编曲关系按已确认的适用曲目应用 |
| 同名原版、再版、现场版 | 分别保留发行版本 | 不因名称或音频指纹相同就合并专辑或删除歌曲 |

归属依据依次考虑用户明确指定、可信发行 ID、文件中一致的专辑信息，以及目录、曲目顺序、碟号等辅助证据。来源互相冲突时进入待核对，不凭某位艺人出现次数最多就决定专辑署名。

首批保留“待核对的发行版本”，不要求所有音乐都联网认领成功才允许播放。基础信息足够时可保守入库；会导致归档歧义或内容冲突的项目沿用待整理流程。

新文件在发布到正式托管目录前确定归档依据；既有音乐的数据库归组调整不自动搬文件。仍使用现有“专辑艺人 / 专辑 / CDxx / 曲号 - 歌名”结构，不在这批引入复杂命名模板。不同发行版发生同名路径冲突时展示版本与路径候选，不能直接覆盖。

## 5. 封面：专辑独立选图，歌曲可以继承或保留个性

### 5.1 专辑封面

推荐优先级：人工指定并保留的选择 → 明确的专辑目录封面 → 同专辑的内嵌正面图片候选 → 已核对发行版本的在线正面封面 → 占位图。

目录候选继续识别 `cover`、`folder`、`front` 等名称；多碟的共同封面只在已确认的专辑与托管路径边界内解析，不任意向上级目录找图片。碟片独立封面首批保留为候选，专门的碟片编辑界面后置。

同专辑有多张不同图片时，先判断正面类型、来源与发行版本，再比较尺寸和清晰度。多首包含相同图片可作为线索，但不以多数票保证它一定正确。存在冲突时保留候选，不自动让第一首歌曲的图片决定整张专辑。

无正面标记但唯一有效的内嵌图片可作为本地回退，来源记为未确认类型；多张无类型图片需要选择候选。明确标为背面、册页等的图片保留，不默认提升为正面封面。

### 5.2 歌曲封面模式

| 模式 | 行为 | 适用情况 |
| --- | --- | --- |
| 自动，已确定默认 | 本曲有效的内嵌正面图片 → 本曲同名图片 → 专辑封面 → 占位 | 保留现有歌曲差异，自动补齐缺失 |
| 跟随专辑 | 直接使用专辑当前封面 | 希望整张专辑统一显示 |
| 独立指定 | 使用这首歌选定的图片，默认锁定 | 单曲封面、自定义图片或特殊版本 |

手动换专辑封面时，先影响“跟随专辑”的歌曲和缺少本曲图片的自动模式歌曲。需要覆盖本曲已有图片时，显式执行“统一封面”：

- **仅补缺失**：不改变已有有效封面的歌曲。
- **全部未锁定歌曲跟随专辑**：展示受影响歌曲和例外后，将它们切换到跟随模式；保留原始图片以便撤销。

两种操作均先在数据库修改选择，不把图片立即嵌入每个 FLAC/MP3。播放列表卡片、全屏毛玻璃和当前歌曲图片都使用同一份生效封面，更新图片不重新加载音频。

### 5.3 图片保存与候选

原图按内容哈希去重保存，曲目和专辑引用同一个图片资产；缩略图是可重建缓存。用户上传或选定的原图不能被“清理缩略图缓存”删除。记录来源、原始位置/来源标识、尺寸、哈希和选择理由，统一做图片格式、大小、像素及解码校验。

在线图片先取得受控的本地副本，核验后再引用，避免每次播放都依赖外站。已有音乐离线可播放，在线来源失效不应让已保存封面消失。

歌曲与专辑分别解析图片可参考 [Navidrome artwork](https://www.navidrome.org/docs/usage/library/artwork/)。本方案的人工选择、锁定、批量统一与资产保存规则需要自行实现。

## 6. 自动化：默认少打扰，疑难项有依据

### 6.1 默认策略

| 输入或操作 | 推荐处理 | 是否需要逐项确认 |
| --- | --- | --- |
| 明确多值标签、空白清理、本地图片读取与去重 | 自动解析，保留原始观测 | 不需要 |
| 已确认专辑内缺封面的歌曲 | 按模式回退专辑封面 | 不需要 |
| 一次确认后重新执行相同本地规则 | 幂等执行，无变化则跳过 | 不重复询问 |
| 联网补齐词曲编、发行信息或封面 | 形成候选与字段差异，可按专辑或批次确认 | 默认需要 |
| 替换已有信息、合并身份、拆合专辑 | 展示依据、影响范围和冲突 | 需要 |
| 标签写回、已有文件移动/重命名 | 独立显式任务，检查版本并准备恢复材料 | 需要明确操作 |

后续可以增加可选的“联网自动补空”策略，但前提是完成真实曲库评估，并满足身份/录音/发行证据、字段未锁定、没有有效现值等确定条件。模型自行输出的“95% 置信度”不作为自动应用资格。

### 6.2 生效值与锁定

生效顺序为：人工覆盖 → 经确认或明确授权策略应用的修复值 → 当前文件观测值 → 缺省显示。**未应用的 AI/联网建议单独保存，不参与生效值计算。**

用户明确清空一个字段也属于有效修正，不能被自动补空再次填回。提供“恢复文件值/恢复自动处理”作为明确动作。锁定当前文件值时保存其快照，防止文件随后变化而让锁定失效；批量和自动任务跳过锁定项，单曲修改需明确解锁。

每次应用记录对象 ID、字段前后值、来源、证据、操作者、编辑版本和批次 ID。撤销前核对当前版本，不能撤销一个旧批次时顺带覆盖用户后来的修改。外部候选按文件与实体版本失效，旧建议不能直接应用到已变化的文件。

### 6.3 触发和状态

新导入后自动执行本地解析、归属预检和封面候选处理；人工修改后只重算受影响对象。管理员启用来源后，新导入自动查询联网资料并生成建议；已有曲库由管理员手动批量查找。联网结果仍经确认后应用，失败有重试上限和退避。

后台定时任务只推进待处理项、重试失败项和检查外部候选有效期，不每天给全库改名或反复覆盖元数据。后台任务至少区分排队、执行中、待确认、已应用、无变化、冲突、部分失败和中断；逐项展示原因，其他歌曲继续入库与播放。

## 7. 联网来源与 Agent 的推荐位置

用户已选择第二批首先接入 MusicBrainz，再加入 Last.fm 元数据与收听同步。MusicBrainz 用于身份、录音、发行版本及已有贡献关系，Last.fm 补充资料与用户收听；不承诺两者能补齐全部中文词曲编。已确认配套接入 [Cover Art Archive](https://musicbrainz.org/doc/Cover_Art_Archive/API)，缺少本地封面时查询已匹配发行的封面候选，确认后应用；[AcoustID](https://acoustid.org/) 保留为后续录音识别候选。具体前后端分工、授权、提交规则和豆瓣边界见 [MusicBrainz 与 Last.fm 接入设计](../architecture/metadata-providers-and-lastfm.md)。

已对许嵩《山水之间》做单曲只读核对：MusicBrainz 有基础信息，但该录音未返回词曲编关系；CAA 数字发行无封面、CD 版有封面；酷狗和 Shazam 页面能提供更完整署名。详细实体、日期差异及边界见 [数据源样本记录](../research/metadata-source-sample-shanshui-zhijian.md)。这说明需要按字段及发行版本选来源，单曲命中不能代表中文曲库整体覆盖。

| Shazam | [ShazamKit](https://developer.apple.com/shazamkit/)提供 Apple 平台和 Android 的识曲 SDK；[SHMediaItem](https://developer.apple.com/documentation/shazamkit/shmediaitem)公开基础曲目元数据 | 公开字段列表未列出完整作词、作曲、编曲、制作等署名；未验证适合 Python 服务端的完整署名查询接口 | 网页资料研究候选，非已确定依赖 |
| MusicBrainz／CAA | 有官方文档与查询接口；本次已查询基础曲目、发行和封面 | 中文署名覆盖不足；已接入候选查询；真实曲库匹配覆盖率尚待验收 | MusicBrainz 已选为首个来源，CAA 配套接入已确认 |
| Last.fm | 官方资料查询、用户授权、Now Playing 和 Scrobbling API | 尚未配置 Key、联调资料或验证用户授权；不承诺完整中文创作署名 | 已实现基础接入，真实账号仍待配置验证 |
| 豆瓣 | 官方旧客户端包含音乐查询与 OAuth2 示例 | 当前音乐 API 开通、配额及登录提额均未确认；网页登录 Cookie 不是 API 授权 | 后续研究候选 |

“未找到”仅描述本次公开文档核验结果，不断言平台不存在合作方接口。第三方封装、客户端内部请求和网页解析必须分别标明，不能称为官方公开接口；若要采用，先单独验证实际字段、运行方式及维护成本。

下一步按已选来源验证凭据、实际响应字段和连续查询可用性，再用 20–30 首有已知答案的中文样本比较“检索命中、字段完整、版本正确、封面可得、接入稳定”。当前没有验证通过的完整中文词曲编自动补全来源，用户完整曲库的覆盖率也尚未测定；来源选择已确认不等于适配器已实现。

### 7.2 Agent 的职责

规则服务负责格式、身份约束、权限、版本和应用；Agent 负责检索编排、候选比较、解释及生成草案。网页、Agent 与未来 MCP 共用同一业务服务。Agent 不直接改 SQL、移动文件或绕过锁定；框架延续 [既有 Agent 设计讨论](../decisions/0002-ai-connections-and-agent.md)，本次不重新选框架。

联网前由管理员启用来源，明确发送哪些标签或指纹；默认不上传音频、封面原图或整份私人曲库给模型。模型不可用时，本地解析、已有整理结果和基础播放继续工作。

## 8. 网页交互建议

**歌曲编辑**：基础信息、贡献者、封面、歌词。贡献者每行选择角色和身份，可调整顺序；封面显示当前模式、来源、候选和锁定状态。

**专辑编辑**：署名、版本说明、归属、封面和受影响歌曲。修改专辑艺人只影响专辑归属及明确应用的专辑字段，不自动把整张专辑的歌曲演唱者改成同一个人。专辑级词曲编批改需选择实际适用歌曲。

**待整理页面**：按专辑/批次分组，显示已自动完成、待核对和失败项；对比旧值、建议、新封面与依据，可选择部分字段应用，支持暂不处理。图片选择即能预览，不要求下载整首歌再上传。

管理和共享元数据修改要求管理员；普通用户可浏览贡献关系和生效封面。收藏、歌单、收听数据仍按用户隔离。进入管理、保存和刷新图片不打断当前播放。

客户端需要新增贡献角色、身份、封面模式及修订信息时，先写正式 API 契约；原生客户端由独立工作接入。遇到接口不兼容直接说明升级要求，不用伪造字段或隐藏角色来强行兼容。

## 9. 分期与验收

| 阶段 | 建议交付内容 | 完成后能做什么 |
| --- | --- | --- |
| 第一批 | 稳定贡献者/专辑记录、四类角色、多值标签映射、专辑级编辑、封面模式与候选、锁定和批次撤销 | 离线也能在服务端把多艺人和封面整理好，自动处理本地确定项 |
| 第二批 | MusicBrainz 与 Last.fm 元数据、CAA 封面候选、整批建议预览、按用户 Last.fm 已听记录与正在播放同步、Agent 受控工具 | 新导入自动查询、旧库手动批量查询，确认后应用资料，并按用户授权同步播放 |
| 后续独立交付 | 副本标签写回、已有目录重整、经评估后可选的联网自动补空 | 显式把数据库结果落到托管副本，进一步减少人工确认 |

第一批虽包含多项能力，可按“数据与迁移 → 贡献者/专辑编辑 → 封面 → 自动任务/撤销”的顺序分 PR 实现，不要求一次大改交付。

第二批的资料来源按 D6、D7 确定为 MusicBrainz 与 Last.fm，CAA 配套补充缺失封面，并加入按用户授权的已听记录与正在播放同步；查询触发和封面确认遵循 P1–P3。指纹辅助仍为后续候选，不作为首期联网完成条件。实施前先按统一字段映射确定资料语义，接口与客户端更新按单独契约推进。

### 9.1 迁移要求

固化已有派生身份为可持久引用的记录，新实体生成稳定 ID；改名后不重新按名称计算 ID。历史上误并或拆散的专辑通过单独预览修正。迁移保留曲目 ID、用户覆盖、收藏、歌单和收听记录，不把身份合并当成音频去重，也不在迁移时搬动媒体文件。

既有人工修正应迁移为保留优先级的覆盖值；新扫描和自动任务不得将其当成可覆盖的空白。实际表结构、数据库升级号和接口在实施时确定，本文不是数据库迁移脚本或已生效 API。

### 9.2 必测场景

1. 单曲多人演唱、多人作词和一人兼任多个角色，顺序与角色过滤正确，曲目计数不重复。
2. `AC/DC` 等名称、多值标签与 `A feat. B` 展示署名并存，名单不误拆。
3. 同名人物不误并；繁简名/艺名确认关联后，保留原署名，筛选能找到同一身份。
4. 个人专辑中的合作曲、联名专辑、群星合辑、影视原声分别正确归组，曲目演唱者不被批量替换。
5. 同名不同发行、现场/录音室、翻唱版本有冲突时给出候选，不误合并或删除。
6. 一张专辑的不同内嵌封面、缺封面、单曲独立图片和多碟目录，三种模式均按规则回退。
7. 换专辑封面、“仅补缺失”、“全部未锁定跟随”和撤销，影响范围一致；图片刷新不重载音频。
8. 人工锁定、明确清空、重扫、重复导入和重复自动任务后，生效值及任务结果稳定。
9. 并发编辑、来源文件变化、旧建议应用、旧批次撤销、任务中断均反馈冲突或实际逐项结果。
10. 断网或模型不可用时，本地处理及已有音乐播放可用；无外部结果时保留未知信息。
11. 数据迁移前后核对曲目与个人数据引用，导入源和托管音频哈希不因数据库整理改变。

实现时按项目约定运行 `make ci` 与适用的容器验证；使用覆盖上述场景的合成库，再按既有授权范围对真实旧库做只读候选评估。0.2.2 的部分实现及已执行测试见接入文档；上文完整设计中的其他能力仍待实施与验收。
