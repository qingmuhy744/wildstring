# AI 服务、内置 Agent 与 MCP

日期：2026-10-15；开发范围更新：2026-10-17。状态：AI 连接设置、自然语言找歌与歌单候选已实现；0.4.0 分支增加受控助手、MCP、巡检、通用通知和日志诊断；实现及验证边界见 [运行说明](../architecture/agent-platform.md) 与 [0.4.0 发布说明](../releases/v0.4.0.md)。当前实施顺序及阶段验收以 [完整开发计划](../product/agent-mcp-observability-notifications-plan.md) 为准。

已确认暂不接入 SIWC，继续使用用户配置的 AI API；优先补统一网络、日志与公共工具，开放 Codex 可调用的 MCP，再扩展持久巡检和内置 AI。默认结果通知为服务端站内收件箱，Web／Android 在上线、回前台或恢复联网时拉取；Telegram 为主动启用的首个外部渠道。

## 推荐方向

0.4.0 首版使用有界 Chat Completions 工具循环和独立持久任务；**Pydantic AI** 保留为后续框架候选，尚未引入。它提供结构化输出校验、工具与依赖注入，与本项目已有 Python/FastAPI/Pydantic 业务模型契合。支持多种模型后端与 MCP 工具接入，但具体 API 的结构化输出/工具调用兼容性仍需通过真实模型验证，验证后再锁定依赖；MCP 与公共业务工具不依赖这个框架。官方来源：[概览](https://pydantic.dev/docs/ai/overview/)、[MCP](https://pydantic.dev/docs/ai/mcp/overview/)。此处是项目适配判断，不是性能或成本基准结论。

[LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) 提供持久执行、人工介入和图式编排，适合未来多阶段、可恢复的复杂工作流；当前导入/扫描任务已有独立的确定性执行和持久状态，首个 Agent 先验证检索、建议与预览即可，不因选择框架就重写曲库任务。

## 统一业务能力，两种调用入口

普通网页、内置 Agent 和后续 MCP 适配器都调用同一套业务服务。MCP 是外部 Agent 的工具接口，不代替模型/Agent 编排。框架的 MCP 客户端支持也不等于野弦已经提供 MCP 服务端。

首批可考虑的工具：检索真实曲目 ID、读取观测值/覆盖值、生成修复草案、预览字段差异、保存用户确认的数据库覆盖、生成/保存歌单、提交受控整理任务、查询结果。模型不可直接执行 SQL、任意文件路径、Shell 或自行选择可写目录。

读取/建议和应用修改分别记录。修复草案携带曲目 ID、编辑版本、字段与理由；应用时重新校验归属与版本。外部 Agent 使用单独的受限凭据与工具权限，不直接复用浏览器会话或开放无鉴权 MCP。

只读边界针对导入源，托管副本是允许显式修改的目标。未来标签写回/目录重整仍通过有预览、文件版本检查、备份与逐文件结果的任务服务执行，Agent 不能绕开这些规则。

## 已确认的开发边界

- Codex＋MCP 与内置 AI 使用同一套业务服务，MCP 基础操作不要求配置模型。
- 交互式助手与后台巡检都在本轮范围，先生成草案，确认具体差异后应用；标签写回与移动文件仍后置。
- 默认站内通知可由手机和网页延后拉取，不依赖推送 API；Telegram 由用户选择启用。
- 日志、工具凭据、用户隔离、版本校验、任务预算／取消／恢复和通知投递均有独立验收。
- 用户实际 API 的输出、工具调用、代理兼容性、中文曲库歧义和零虚构 ID 验证后，再锁定框架依赖。具体阶段与测试门槛见完整开发计划。
