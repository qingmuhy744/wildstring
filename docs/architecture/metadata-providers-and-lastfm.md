# MusicBrainz 与 Last.fm 接入设计

日期：2026-10-16。状态：**MusicBrainz、Last.fm 与配套 CAA 接入范围及 P1–P3 行为均已由用户确认；已进入 0.2.2 实现，具体已实现与未验证边界见文末。**

与[自动整理方案](../product/metadata-automation.md)、[标签映射](metadata-field-mapping.md)共用字段语义。服务端统一接入，客户端只对接野弦 API；本机已完成 Last.fm 只读资料查询，真实用户授权与收听外发仍待验证；实现情况见文末。

## 1. 来源范围

| 来源 | 首期用途 | 已核对与未验证的边界 |
| --- | --- | --- |
| MusicBrainz | 搜索曲目/发行候选，关联外部身份，读取已有贡献关系 | 有官方 API；已实查《山水之间》，该记录缺词曲编，不承诺中文完整覆盖 |
| Last.fm | 曲目、专辑、艺人资料、标签、简介；用户授权并启用后同步已听记录与正在播放 | 只读资料查询已验证；真实用户授权与收听外发待验 |
| Cover Art Archive | 缺少本地封面时，按 MusicBrainz 具体发行版获取封面候选，确认后应用 | 配套接入已确认；已实查不同发行版图片可用性，应用内适配和版本匹配尚待验证 |
| 豆瓣 | 保留资料研究候选 | 历史 OAuth / 音乐 API 不能证明当前可申请、可用或登录提额；不加入首期依赖 |
| AcoustID | 本地 Chromaprint 指纹识别录音，衔接 MusicBrainz 资料建议 | 0.2.3 可选接入；只发送指纹和时长，建议确认后应用 |
| 酷狗、Shazam、QQ 音乐、网易云 | 后续分别核验 | 页面、SDK、指纹和完整元数据接口不能混为一谈；尚未确定接入 |

MusicBrainz 的[公开查询](https://musicbrainz.org/doc/MusicBrainz_API)不需要用户登录或 API Key，使用可识别的 User-Agent，按官方[限流要求](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting)控制请求间隔。统一服务端队列协调查询；多进程部署时共享限流状态，不能每个客户端或进程各自并发占用同一出口的额度。

Last.fm 的 [track.getInfo](https://www.last.fm/api/show/track.getInfo)、[album.getInfo](https://www.last.fm/api/show/album.getInfo)要求 API Key，查询本身不要求每位用户授权，支持按名称或 MBID 查询。返回的艺术家/曲目名称修正、标签和简介均保留来源，不当作已经核实的词曲编关系；缺失字段保持未知。

Last.fm 响应可包含图片地址，但图片的下载、持久保存和写入音频不能仅凭响应有 URL 就视为已确认可用。其[条款](https://www.last.fm/api/tos)包含图片排除、数据量上限、缓存和来源链接要求；首期封面优先本地及经核对的发行图片，Last.fm 图片使用能力需单独核验。通用缓存按来源分别配置，不全库无限保存 Last.fm 原始响应。

## 2. 前后端职责

| 位置 | 职责 |
| --- | --- |
| 服务端实例设置（管理员） | 启用来源、配置 Last.fm 应用 API Key / Secret、连接测试、限流和缓存；凭据留在私密 `.env` 存储，接口仅返回配置状态 |
| 每位用户的个人设置 | 连接或断开自己的 Last.fm，分别启用收听同步和“正在播放”发布；管理员配置来源不等于所有用户自动同意同步 |
| 网页与原生客户端 | 打开授权入口、显示连接状态；上报真实播放事件与累计实际收听时间；复用稳定播放会话 ID |
| 服务端业务与后台队列 | 换取并私密保存每用户 session key、签名请求、生成资料候选、检查权限、持久提交任务、响应解析和有限重试 |

API Key 的保密程度与 Secret 不同，但全部查询仍经服务端，便于缓存和配额管理。Secret、用户 session key 不下发客户端，不写普通日志；私密会话存储与数据库用户记录用引用关联，遵循仓库凭据存放约定。

Last.fm 采用其[授权协议](https://www.last.fm/api/authspec)，不笼统称为标准 OAuth2。用户在 Last.fm 页面登录并授权，服务端完成换取 session key；授权请求要绑定当前野弦用户并校验短时效的一次性状态，不能让回调绑定到其他用户。断开连接后停止同步并取消未发送任务；重新连接不默认补传历史记录。

## 3. 元数据闭环

管理员启用来源后，新导入自动触发资料查询并生成建议；已有曲库提供管理员手动选择歌曲或专辑的批量查询入口。服务端依据现有标签/外部 ID 查询 → 显示版本候选与字段差异 → 确认后更新数据库。自动查询不等于自动应用；生效模型使用统一标签语义，每字段保留来源、外部实体、采集时间和当时编辑版本。

本曲或专辑已有可用本地封面时继续使用本地选择；缺少本地封面时，从已匹配发行版查询 CAA 候选，核对版本并确认后应用。CAA 无图时保留缺失状态，不为了补图自动改认另一个发行版；跨发行版封面仅作为有明确来源的候选。

MusicBrainz 的录音、发行版、专辑组和作品 ID 分开保存。相同录音被不同专辑收录时仍核对发行归属。Last.fm 仅有艺人+歌名的匹配时保留歧义；名称自动纠正属于建议，不能覆盖人工锁定值。

查询、图片失败或模型不可用不阻断播放。资料来源的全站播放量与本地用户统计分别保存；不因用户连接 Last.fm 就覆盖共享曲库或将外部收藏自动合并到本地“♥ 我喜欢”。

## 4. 收听同步

复用当前 [POST /api/v1/listening](../../contracts/personal-library.md) 的 UUID 会话及累计实际收听思路；具体字段扩展另写 API 契约。现有实现没有播放事件类型、客户端标识和显式开始时间，也没有 Last.fm 外发队列，不能直接宣称现接口已支持同步。

建议补充开始、播放、暂停和结束状态及开始时间。服务端从真实曲目 ID 读取生效标签，验证当前用户、会话归属、时间和可接受的收听增量；不接受客户端代替其他用户选择 Last.fm 账号。

按官方[Scrobbling 规则](https://www.last.fm/api/scrobbling)：歌曲时长须大于 30 秒；实际收听达到曲长一半或 4 分钟中的较短值，才具备提交资格。暂停、缓冲和拖动进度不累计；时长不明先不提交。现有本地播放次数阈值与 Last.fm 资格分别检查，不修改本地历史计数去迎合外站。

“正在播放”与已收听记录分别处理：前者按当前会话发布且失败后不排队补发；后者达到资格后持久入队。手动重播生成新会话，可以形成新的收听记录。重试同一次会话不能重复生成外发任务；跨设备接力只有共用同一次播放身份时才能去重，不按“同曲、相近时间”误删真实重复收听。

任务保存用户、绑定账号身份、播放会话、开始时间和提交时的元数据快照；发送前检查仍已授权且启用。同一会话使用唯一约束防止本地重复入队；第三方请求超时后的接收状态可能不明确，不能承诺端到端严格仅执行一次。保留同一开始时间及快照处理重试，不重生成新播放记录。

检查 Last.fm 业务响应及逐项接受/忽略结果，HTTP 200 不直接当成功。临时故障退避重试，失效授权要求重新连接，永久错误停止；进程重启不丢待发任务。状态至少有待提交、已接受、已忽略、需重新连接、提交结果不明、失败；本地收听统计独立成功，不因外站失败回滚。

## 5. 豆瓣登录提额的边界

[豆瓣官方旧 Python 客户端](https://github.com/douban/douban-client)存在音乐查询和 OAuth2 示例，但仓库已归档，历史代码要求应用 API Key / Secret 与授权 token。浏览器登录 Cookie 和应用 OAuth/API 配额属于不同机制，不能由登录成功推导出查询额度提高。

本次旧开发者文档和音乐 API 的网页读取未成功；这只能记作“未验证”，不能据此断言全部服务停用。本次未使用豆瓣账号登录，也未实测登录前后配额。未找到当前公开音乐 API 的申请途径、现行配额和登录提额承诺，因此首期不依赖豆瓣；后续可以独立验证按条目补充资料的方式及字段覆盖。

1. 先完成本地字段、贡献者和图片模型；映射按 Mp3tag / Picard 核对，保留既有曲目 ID 与人工覆盖。

4. 按用户绑定 Last.fm，扩展播放事件与持久提交队列，实现已听记录及正在播放的独立开关；网页接入，原生客户端由独立工作按正式契约更新。
5. 验证权限隔离、账号解绑、暂停/seek/短曲不误报、真实重播、重复心跳、失败重试、进程重启、业务忽略与响应不明。

本节记录初始规划。当前代码实现、只读查询联调与真实用户授权的验证边界以文末为准。

## 0.2.2 实现状态与使用入口

本节优先于上文的设计目标。实现代码、模拟测试和真实第三方账号验证分别记录：

- 已接入 MusicBrainz 曲目及发行版候选、已有创作关系；Last.fm 首批读取曲目标签与简介；CAA 按发行版提供封面候选。专辑/艺人完整资料页、声纹匹配、模糊合并及批量自动应用仍在后续范围。
- 管理员在「曲库管理 → 设置 → 联网资料」启用服务、设置 Last.fm Key / Secret 与公开访问地址；默认关闭。首次启用将已有曲目标为旧库，管理页可查询本页（每批最多 100 首）；之后新入库自动排队。查询状态和候选在歌曲编辑的「联网建议」中查看。
- 资料逐字段勾选后应用，显式选择可替换人工值；保存来源、原值快照和版本。过期建议不能覆盖新编辑。不写音频标签、不改文件路径。历史回滚界面、独立字段锁和稳定专辑实体仍待开发。
- 每用户在账号设置连接 Last.fm；Android 设置也提供连接、刷新、解绑和两个同步开关。授权后两个开关默认关闭。已听记录持久入队并退避重试；正在播放只发送新近的活动会话，不补发旧状态。业务忽略记为失败，失效会话要求重新授权。本地唯一键去重，网络超时不保证第三方严格仅执行一次。
- 已实现按演唱、作词、作曲、编曲查询，以及文件原生多值、署名、总曲数/碟数、日期精度和外部标识读取。旧库需完整重扫读取新增字段，人工覆盖保留。歌曲独立封面优先，缺失时读取同专辑封面；CAA 应用后的图片独立持久保存。
- 使用隔离数据库真实读取《山水之间》的 MusicBrainz 记录与 CAA 发行封面。2026-10-17 使用私有应用凭据、隔离数据库与现有适配器完成 Last.fm 只读查询：《山水之间》能返回许嵩的曲目记录，但该次结果无标签、无简介；对照曲目可返回标签和简介。应用凭据仅保存在被 Git 忽略的本机配置中。真实用户授权、正在播放和已听记录外发仍待联调；这些流程目前通过模拟响应验证。

### 网页代理与 Docker 环境变量

联网代理有三种模式：`environment`（默认，跟随环境变量）、`custom`（网页指定）和 `direct`（直接连接）。HTTP/HTTPS 目标均支持 HTTP 代理和 CONNECT，地址如 `http://proxy.example:7890`；有认证时对用户名密码进行 URL 编码。SOCKS 和 TLS 代理端点尚未支持。

环境模式按目标协议读取 `HTTP_PROXY` / `HTTPS_PROXY`，缺少对应值时回退 `ALL_PROXY`；也支持小写变量，按 Python 的标准规则优先小写。`NO_PROXY` 用于绕过代理。Docker Compose 将这些变量传入容器，`DOCKER_HTTP_PROXY` / `DOCKER_HTTPS_PROXY` 仍只用于镜像构建。网页指定模式优先于环境代理；直接连接不读取代理地址。手动代理和 Last.fm 凭据保存到 `/data/providers/.env`（0600），公开 API 只返回配置状态。代理错误不回显带密码的 URL。

home 上 Emby 的只读核对显示其代理通过 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 和 `NO_PROXY` 注入，代理是局域网 HTTP 地址；野弦可采用相同变量方式。没有修改服务器部署，也没有复制其认证信息。

容器中的 `127.0.0.1` 指容器本身。在本机 Docker 可使用 `host.docker.internal`，Linux Compose 已增加 host-gateway 映射；home 部署可填写容器能访问的局域网代理地址。以下值均为占位示例，不包含实际凭据：

```dotenv
HTTP_PROXY=http://192.168.8.3:10801
HTTPS_PROXY=http://192.168.8.3:10801
ALL_PROXY=http://192.168.8.3:10801
NO_PROXY=127.0.0.1,localhost,host.docker.internal
```

代理仅用于外部资料、封面下载与 Last.fm 授权/同步，不代理音乐串流、前端 API 或 AI 连接。反向代理访问日志也应隐藏 `/api/v1/lastfm/callback` 的查询参数；内置 Uvicorn 启动入口已做脱敏。

## AcoustID 与手动刷新（0.2.3）

2026-10-17 用户提供应用 Key 并确认接入。新增可选 AcoustID lookup、只读 fpcalc 计算与缓存，复用 MusicBrainz／CAA 的建议和确认流程。MetaBrainz 是维护 MusicBrainz 等项目的基金会；不需要额外申请一个通用的 MetaBrainz Key。

| 准备项 | 查询识别需要什么 |
| --- | --- |
| AcoustID Application API key | 登录后[注册应用](https://acoustid.org/new-application)，作为 `client` 参数使用 |
| AcoustID User API key | 仅向服务提交新指纹时需要；只查询不需要 |
| MusicBrainz | 普通公开资料查询无需 API Key；继续提供应用 User-Agent，并控制到每秒最多一次请求 |
| Chromaprint / fpcalc | 在服务端从托管副本计算指纹，不需要申请 API；Docker 原镜像已增加工具，原生 macOS／Linux 可单独安装 |

实现流程为本机计算指纹与完整时长 → AcoustID 返回录音候选 → 衔接现有 MusicBrainz／CAA 建议，按录音与发行版分别展示相似度及来源。只调用 lookup，不调用 submit；识别默认关闭，保存 Key 不自动启用外发。AcoustID 公开免费服务用于非商业场景，官方当前要求每秒不超过三次请求；应用继续保守地按每秒约一次共享限流。

网页新增歌曲、专辑与整库的手动元数据更新，支持只查缺失／查询全部、绕过联网缓存和后台任务状态；MusicBrainz／Last.fm 来源优先级可拖动排序。人工值及本地封面保留，联网结果仍确认后应用。规则、契约和部署依赖见 [元数据刷新与指纹识别](../product/metadata-refresh-0.2.3.md)。

验证边界：本机合成音频已真实生成指纹并通过 AcoustID lookup（无匹配属于正常结果），说明应用 Key 可用；官方公开指纹样例识别到两个录音候选，并成功衔接 MusicBrainz。用户明确允许私人曲库测试后，使用独立临时数据库只读测试崔健《新长征路上的摇滚》：AcoustID 返回两个录音候选，相似度均约 0.98；MusicBrainz 返回六个发行版候选，包含词曲、演唱等资料，无查询警告。测试未应用建议，前后音频 SHA-256 一致。单首成功不等于全库覆盖率，资料完整度和发行版仍需人工核对。联网错误和多候选、错误标签、缺失字段保护与显式应用使用隔离回归验证。生产服务是否启用，以管理员设置为准，代码接入不等于已部署。
