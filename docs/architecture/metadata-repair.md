# 服务端元数据修复与整理

状态：规划中，尚未实现。来源：用户希望直接在服务器整理曲库，减少下载到电脑、用 mp3tag 修改后再上传的重复传输。

## 三层数据

1. **文件观测值**：扫描获得的原始标题、艺人、专辑、编号、封面等，保留读取时间与文件版本。扫描本身始终只读。
2. **用户覆盖值与修复建议**：手动修改、批量编辑、来源匹配或 AI 建议，记录来源、依据与字段差异。人工锁定值优先，重扫不会覆盖。
3. **写回任务**：用户显式选择将哪些字段写入服务器上的音乐文件。数据库覆盖可独立使用，不必立刻写回文件。

当前已支持按已有标签导入、整理托管副本并扫描文件观测值；用户覆盖、建议、标签写回和已有副本重整均待后续实现。

## 交互与执行

选择曲目 → 手动或批量编辑/请求匹配 → 预览修改前后差异 → 选择仅保存数据库或写回标签 → 服务端执行 → 复查和重扫 → 返回逐文件结果。

音频不通过浏览器下载再上传。标签更新和必要的文件重写在服务端执行；服务器磁盘或挂载的 NAS 仍会产生读写。封面从浏览器上传时只传图片及结构化修改内容。

第一版先支持标题、艺人、专辑、专辑艺人、轨道/碟片编号与封面。保留真实多艺人值，不用斜杠强行拆分 AC/DC 等名称。自动匹配是可替换来源，低置信度与多发行版本展示候选，不自动覆盖。

## 写回前提

- 管理员权限与独立的媒体写入开关，默认关闭。导入源始终只读；托管目录用于导入副本，后续标签写入额外受应用权限和显式任务控制。
- 使用真实曲目 ID 定位文件，写回前重新检查文件版本和路径边界。复制未完成或被外部工具更改的文件应产生冲突，不能使用过期建议覆盖。
- 保存原标签快照；涉及文件重写或移动时，先准备可恢复备份。备份保存在音乐目录之外，磁盘空间不足时不启动任务。
- 同文件的修复、外部变化与重扫需要协调；任务记录逐文件结果，重启后可重试，不能把部分成功当全部成功。
- 写回后重新读取并核对目标字段，保留权限和未知标签，不未经选择删除歌词、封面等内容。
- 变更在服务器完成后，保留曲目 ID 并刷新曲库索引；支持查看执行记录和恢复操作。

此处是设计约束，当前导入器能创建托管副本，尚无元数据修复写回接口；导入源仍保持只读。

## 文件名与目录

重命名、按艺人/专辑整理目录属于单独任务，需要处理命名冲突、非法字符、跨文件系统移动与中断恢复。“仅保存”不隐式移动文件；用户选择“保存并整理”时，将元数据保存和重新整理作为同一次操作的可恢复任务。

当前扫描器在同一根目录、同一相对路径的重扫中保留 ID；外部重命名暂按旧文件缺失与新文件导入处理。应用自身的整理任务将来必须显式维护 ID 与路径映射，外部移动识别再参考 Navidrome 的 persistent ID 方案。

## 导入源与托管副本

用户已确定使用托管模式：导入源（data/ 或其他挂载）始终只读，导入时复制并整理到运行数据卷的 library/。之后播放、标签修复和目录整理都只作用于托管副本；修正与 AI 建议先存数据库，明确应用才写入副本。重复导入保留已有副本修改；源变化报告冲突。原件不参与写回任务。详见 [托管规则](../../contracts/managed-library.md)。

## 补全信息后的重新整理（规划，未实现）

采用事件触发，不周期性给全库改名。修改标题、艺人、专辑或曲号后，“保存并整理”根据最新生效元数据计算受影响曲目的目标路径；无路径变化则直接完成。只有扫描观测到的外部标签变化先生成待处理记录，不未经明确操作搬动文件。

单首任务可立即执行，批量可选择立即或实例维护时段。定时调度只推进待处理任务、重试暂缓项和核对一致性，不扫描全库并反复执行所有改名。人工锁定路径优先；同名冲突、磁盘不足、文件版本变化或正在占用时暂缓并反馈。

执行前检查版本、生成原/目标路径差异并准备恢复材料。文件移动和数据库提交有独立阶段与补偿记录；成功后保留曲目 ID、歌单引用和播放队列，更新 tracks、导入源映射与专辑索引，防止下次导入重新指向旧路径。歌词随同名音频重命名；共享封面仍有其他引用时保留原位置，必要时复制。任务幂等，重启不能重复移动或把部分成功当整体成功；导入源绝不参与移动。
