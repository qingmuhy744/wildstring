# 服务端元数据修复与整理

状态：规划中，尚未实现。来源：用户希望直接在服务器整理曲库，减少下载到电脑、用 mp3tag 修改后再上传的重复传输。

## 三层数据

1. **文件观测值**：扫描获得的原始标题、艺人、专辑、编号、封面等，保留读取时间与文件版本。扫描本身始终只读。
2. **用户覆盖值与修复建议**：手动修改、批量编辑、来源匹配或 AI 建议，记录来源、依据与字段差异。人工锁定值优先，重扫不会覆盖。
3. **写回任务**：用户显式选择将哪些字段写入服务器上的音乐文件。数据库覆盖可独立使用，不必立刻写回文件。

当前首个扫描单元只实现文件观测值；用户覆盖、建议与写回均待后续实现。

## 交互与执行

选择曲目 → 手动或批量编辑/请求匹配 → 预览修改前后差异 → 选择仅保存数据库或写回标签 → 服务端执行 → 复查和重扫 → 返回逐文件结果。

音频不通过浏览器下载再上传。标签更新和必要的文件重写在服务端执行；服务器磁盘或挂载的 NAS 仍会产生读写。封面从浏览器上传时只传图片及结构化修改内容。

第一版先支持标题、艺人、专辑、专辑艺人、轨道/碟片编号与封面。保留真实多艺人值，不用斜杠强行拆分 AC/DC 等名称。自动匹配是可替换来源，低置信度与多发行版本展示候选，不自动覆盖。

## 写回前提

- 管理员权限与独立的媒体写入开关，默认关闭。日常 API/扫描继续使用只读音乐挂载，写入进程单独启用受限的可写挂载。
- 使用真实曲目 ID 定位文件，写回前重新检查文件版本和路径边界。复制未完成或被外部工具更改的文件应产生冲突，不能使用过期建议覆盖。
- 保存原标签快照；涉及文件重写或移动时，先准备可恢复备份。备份保存在音乐目录之外，磁盘空间不足时不启动任务。
- 同文件的修复、外部变化与重扫需要协调；任务记录逐文件结果，重启后可重试，不能把部分成功当全部成功。
- 写回后重新读取并核对目标字段，保留权限和未知标签，不未经选择删除歌词、封面等内容。
- 变更在服务器完成后，保留曲目 ID 并刷新曲库索引；支持查看执行记录和恢复操作。

此处是设计约束，当前尚无写回接口，也未放开任何音乐目录写权限。

## 文件名与目录

重命名、按艺人/专辑整理目录属于单独任务，需要处理命名冲突、非法字符、跨文件系统移动与中断恢复。它不能隐含在“修复标题”操作里。

当前扫描器在同一根目录、同一相对路径的重扫中保留 ID；外部重命名暂按旧文件缺失与新文件导入处理。应用自身的整理任务将来必须显式维护 ID 与路径映射，外部移动识别再参考 Navidrome 的 persistent ID 方案。
