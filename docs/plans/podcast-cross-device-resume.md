# 播客跨设备续听

## 目标

四端都能在另一台设备听过之后正常续听，不需要手动刷新页面，并且不会把别处已经标为已听完的单集改回未听。

现状按当前实现核对如下（`main` 7c5d4b5）：

| | 开播前先读服务器 | 先按旧进度出声再跳 | 已听完会被改回未听 | 切回页面自动更新 |
| --- | --- | --- | --- | --- |
| Web | 是 | 否 | 是 | 否 |
| Android | 是（等待上限 6 秒） | 被 pause 挡住，存在极短漏音，未实测 | 是 | 否 |
| macOS / iOS | 否 | 是 | 是 | 否 |

具体位置：

- 服务器：新会话的非片尾事件一律重算 `completed`，见 `backend/src/wildstring/podcast_progress.py:103-108`。任何端用旧缓存从开头播放都会清掉已听完。
- Android：`frontend/android/app/src/main/java/com/wildstring/app/data/PodcastProgress.kt:91-113` 先读后播。静默改写版本、重传旧位置在 `:155-165`，同一集已在播放器里时不会重新准备（`playback/PlaybackService.kt:278-282`）。节目页「继续」读缓存（`ui/PodcastScreen.kt:1202-1206`），详情按 `loadedDetails` 缓存（`PodcastBrowser.kt:83-85`），无前台恢复刷新。
- Apple：`frontend/ios/WildStringKit/Sources/CorePlayback/PlaybackService.swift:1543-1587` 先按旧位置加载音频，再在后台读服务器并校正。macOS「继续」挑列表里第一个听了一半的集（`MacPodcasts.swift:491`），续听对话框用页面旧数据（`:108-111`），窗口不刷新。
- Web：`frontend/web/src/player.tsx:588-596` 先读后播；已听完从 0 播并上报，清掉已听完。切回标签页不刷新（`podcasts.tsx` 无 `visibilitychange`）。

## 不碰的边界

- 不改历史提交与已发布标签，不改 `contracts/podcast-progress.md` 之外的进度语义，不做跨设备实时推送或播放中轮询别的设备。
- 不回溯修正已有书签：已停在片尾余量内但未标已听完的旧记录保持原样。
- 片尾余量标已听完的规则已在 PR #148 处理，本方案不改它的阈值与触发事件。两者都会改 `save_progress`，以 #148 先合入为前提。
- 不改导入源、托管曲库与下载文件，只改进度读写和页面刷新。

## 方案

### 1. 服务器按意图保护已听完

`PUT /api/v1/podcasts/episodes/{episode_id}/progress` 增加可选字段 `intent`，取值 `resume` 或 `restart`。

- `resume`：用户点「继续收听」。本次会话的写入不会把已听完改回未听。
- `restart`：用户明确从头播放或标为未听。按现有规则重算。
- 缺省：保持当前行为，老客户端不受影响。

**携带方式**：`intent` 不落库，但客户端要在本次收听的**每一次**写入都带同一个值，包括 `play`、`progress`、`pause`、`seek`、`stop` 和离线补传。只带首个 `play` 不够：后续 `progress` 或 `seek` 会让服务器重算 `completed`，已听完又丢。Android 的 Room 待发送表和 Apple 的本机待发送记录各多存一个值，Android 需要升 Room 版本。

**事件序列语义**（服务器）：

- `intent=resume` 时，未完成→已完成仍然允许：位置真正进到 `ended` 或片尾余量，照样标已听完。
- `intent=resume` 时，已完成→未完成被禁止：任何位置和事件都不清已听完，直到出现一次 `intent=restart` 或缺省 `intent` 的新会话。
- `intent=restart` 只表达这一次会话的意图，不是一次性动作；同一会话后续写入继续以 `restart` 处理。
- 检查点在同一次会话内仍然成立。混用不同 `intent` 的写入，以该次请求的 `intent` 为准。

**发布顺序**：`ProgressWrite` 是 `extra="forbid"`（`backend/src/wildstring/podcast_progress.py:26-27`），新客户端带 `intent` 打到旧服务器会得到 422。因此**先升服务器，再发客户端**。旧客户端配新服务器维持现状。

与 #148 的片尾余量处理汇合在同一处：`resume` 时保留已完成、允许未完成→完成；`restart` 与缺省按现有规则。

### 2. 冲突处理（Android 与 Apple 共用规则）

当前两端都会在 409 时改写版本、开新会话、重传本机位置：Android `data/PodcastProgress.kt:155-165`，Apple `PlaybackService.swift:1615-1640`（`play`/`seek`/`ended` 和播放中的 `progress` 都会重试）。这会让另一台设备刚写的进度或已听完被覆盖。

契约改为：

- 只有服务器当前会话的 `deviceId` 与本机相同时，才允许改写版本重传，且只重传当前这一次写入。
- `deviceId` 不同，且对方会话在 10 分钟内有写入：判定为别的设备正在听这一集，停止本机上传，不重试，不静默覆盖。
- 音频不跳。正在播放的位置保留，本机继续本机播放，只是暂不写服务器。
- **对方安静下来就自动接管**：播放中的进度约 10 秒一次，超过 10 分钟没有新写入视为已离开。此时本机下一次写入不再被拒绝，直接用 `resume` 建立新会话接管，不需要用户操作。
- 用户也可以显式接管：提示条上的「用本机进度」按钮立即以本机位置建立新会话。
- 本机只读是暂时的，最多持续到对方安静下来（约 10 分钟）或用户点按钮，不存在永久不同步。
- 提示条在接管成功后自动消失。

这是**契约变更**：`contracts/podcast-progress.md` 目前写的是「冲突始终询问」，实际四端都没有询问框（Android 的对话框在 0.8.7 删除，Apple 与 Web 只在开始收听时按模式询问）。新规则是「不覆盖正在收听的设备，其余情况自动或手动接管」，契约与四端实现一起改。

### 3. 冲突提示

播放途中撞到别的设备时不弹框，用播放器里一条不打扰的提示条：

> 另一台设备更新了这一集的进度。本机位置暂不保存。

跟一个「用本机进度」按钮。不点就继续播，音频和本机位置都不受影响；接管成功后提示条自行消失。

- 只显示一次，同一集同一次冲突不重复。
- 只读期间每次重试都不再弹第二条。
- 自己设备造成的冲突静默重传，不提示。
- 后台补传时撞到冲突不提示，回到前台按当时状态显示。
- 现有文案 `playerPage.podcastUpdatedElsewhere`「另一台设备刚更新了本集，请重新选择接续位置」要改成上面这句：现在的措辞暗示用户必须动作，实际不动作也能继续听。
- Android 的进度提示通道目前没有接到界面：`data/PodcastProgress.kt:55-56` 的 `message` 在 `ui/` 里没有收集方，`pod_prog_sync_failed_check_network`、`pod_prog_server_update_required` 都是写了没显示。同批接上，提示条复用这个通道。
- macOS / iOS 没有现成的进度提示位置，新增在播放器一栏，沿用现有播放状态的提示样式。

### 4. Android

- 用户主动点播（列表、节目页、待播、迷你播放器与锁屏恢复）时，即使同一集已在播放器中，也重新走一次 `prepare()`；后台自动恢复仍不重读。
- `intent` 映射：
  - 节目页、列表、待播、迷你播放器、锁屏恢复的播放：`resume`。
  - 设置的「从头播放」模式、以后新增的明确重播入口：`restart`。
  - 「标为未听」：`restart`，位置 0，事件 `stop`。
  - 自动续播到下一集：`resume`。
- `prepare()` 读到 `completed=true` 时，不再取 0 并上报 `play`。改为：用 GET 结果按节目列表顺序找当前集之后第一个未听完的集，以 `resume` 播放；没有则停在当前集并显示已听完，不建立会话、不上报。
- 409 按上面第 2 节处理：`deviceId` 相同才重传，不同就停传。`isActiveSession` 不再单独作为重传理由。
- 前台恢复（`ON_START`）时刷新当前节目详情，离上次拉取不到 30 秒不重复拉；保留下拉刷新。
- 「询问接续位置」设置自 0.8.7 起没有对话框，实际等于「自动」。本方案删除该设置项，Android 只保留自动和从头播放两种；`mode == "ask"` 映射为自动，迁移旧值。

### 5. macOS / iOS

- 点「继续」先读这一集进度，再出声，等待上限约 1.5 秒。等待期间用现有缓冲状态，不先按旧位置出声再跳。`bootPodcast` 在开播前完成校正后，启动时的跳位置与「出声后跳一次」一并去掉。
- **已读完的判断只用这次 GET 的结果**，不为了确认状态先 PUT。服务器返回已听完时直接改播下一集，不建立会话、不上报，避免动到会话和最近收听时间。
- `intent` 按会话携带：
  - 「继续」：`resume`，此后本次会话的每次写入都带 `resume`。
  - 「从头播放」：`restart`，仍从 0 开始。
  - 自动续播到下一集：`resume`。
  - 标为未听：`restart`。
- **超时或离线降级**：
  - 读取失败时按本机待发送记录或上次已知位置播放，若本机记录里这一集是已听完，则按已听完处理。
  - 这种情况下不建立新会话，不上报 `play`；后续 `progress`、`pause`、`stop` 也暂不发送，只写本机，避免用旧书签覆盖服务器。
  - 下一次进入前台或网络恢复时，先 GET 一次：服务器仍是未听完，就用 `resume` 建立会话并把本机位置补传；服务器已是已听完，就停传，按已听完处理并提示可以改播下一集。
  - 迟到的读取结果一律丢弃：不进位置、不建会话、不改提示。
- 下一集选择：读到的节目列表里，按现有顺序取当前集之后第一个未听完的集；没有就停在当前集并显示已听完。
- macOS「继续」改为挑最近听的那一集（有进度的集里 `last_listened_at` 最新的那个），全部听完时停住并显示已听完，不退回第一集。
- 窗口重新成为当前窗口（macOS）或场景回到前台（iOS）时静默重拉当前节目，离上次不到 30 秒不重复拉；保留手动刷新。
- 续听对话框和列表行的时间改用刚读到的进度。

### 6. Web

- 切回标签页（`visibilitychange` 回到可见）时静默重拉当前节目，离上次不到 30 秒不重复拉。
- 服务器已是已听完的单集，点播放视为明确从头播放，带 `intent=restart`；其余播放与续听带 `resume`，本次会话的每次写入都带同一个值。
- 读取失败时与 Apple 相同：按本机待发送记录播放，不建立会话、不上报，回到前台或网络恢复后先 GET 再决定是否补传。

### 7. 四端控件统一

三样控件统一到四端都有、名字一致：

| 控件 | 状态 | 要做的事 |
| --- | --- | --- |
| 单集「从头播放」 | macOS/iOS 只在续听对话框里；Web 只在对话框里；Android 没有 | 四端都加到单集菜单，不依赖对话框先弹出 |
| 续听模式（自动 / 询问 / 从头） | Web、Android 有（Android 询问是死的）；macOS/iOS 没有 | 四端都有入口，三个值都生效；Android 恢复询问对话框；账号级同步见第 8 节 |
| 标已听 / 未听 | 四端都有：iOS `PodcastsView.swift:239`、macOS `MacPodcasts.swift:777`、Web `podcasts.tsx:1418`、Android `PodcastScreen.kt:1476` | 不改，只统一文案 |

- Android 的询问对话框：`data/PodcastProgress.kt:36` 的 `EpisodeProgressPrompt` 仍在，只是 0.8.7 删了展示处，接回去即可。位置高于 0 且模式为「询问」时显示「继续」与「从头播放」。
- 单集「从头播放」的行为四端一致：位置 0、新会话、`intent=restart`；文件没下载完时按现有单集播放规则处理。
- 标为未听：位置 0、新会话、`intent=restart`、事件 `stop`；标为已听：`ended`，位置取时长。

### 8. 续听模式按账号同步

四端各有本机存储，同一账号在 Mac 上选「询问」、Android 上仍是「自动」，同一集行为不同。改为账号级：

- 后端新增 `podcast_resume_prefs(user_id PRIMARY KEY, resume_mode TEXT, updated_at TEXT)`，`resume_mode` 取值 `auto` / `ask` / `restart`，默认 `auto`；`SCHEMA_VERSION` 由 52 升到 53。
- 端点：`GET /api/v1/podcasts/resume-mode` 返回当前账号的模式，`PUT` 写入。需要登录，按认证用户隔离。不按节目区分，因为这是账号级偏好。
- 四端都从服务器读，本机只做缓存以便离线启动；写入成功后更新本机缓存，下一次进入设置页时以服务器为准。
- 迁移：首次读到时，如果本机已有旧值，用本机值写一次服务器；之后以服务器为准。
- 老客户端不读这个端点，行为不变。

### 9. 文档

实现落地时同步：`contracts/podcast-progress.md` 补 `intent` 字段与携带方式、冲突规则变更；新增或补充续听模式端点的契约；`docs/product/scope.md` 核对播客设置描述；`docs/releasing.md` 与版本台账按发版节奏处理；本方案状态随进度更新。

## 风险与回滚

- 老客户端不带 `intent`，仍会清掉已听完。服务器只能保护新客户端；彻底解决要等各端升级。不为此做位置启发式，因为「标为未听」同样是新会话从 0 上报，启发式会误伤。
- 发布顺序是硬约束：服务器先升，客户端后发。新客户端先到会让每次进度写入都 422。
- 冲突策略从「询问」改成「不覆盖正在收听的设备，其余自动或手动接管」，最多有约 10 分钟的只读窗口。以提示条说明，不新增对话框。
- 10 分钟接管窗口是启发式：对方只是暂停超过 10 分钟时，会被本机接管。这与「另一台不再听」同义，接受这个误判。
- 续听模式改存服务器后，首次读到时用本机旧值覆盖服务器的风险：只在服务器仍是默认值且本机有非默认值时迁移一次，避免多台设备互相覆盖。
- 恢复 Android 询问对话框会改变默认操作路径（原来静默续听）；旧值不需要迁移，因为 `ask` 一直存在，只是之前没用。
- Apple 开播前等待最多 1.5 秒，弱网下比现在慢。以缓冲状态提示，超时退回本地位置且不上报，不回退成「先出声再跳」。
- 回滚按提交单元进行：服务器 `intent` 缺省行为不变，客户端可单独回退；删除的设置项回退时旧值仍能读出；Room 升版不可逆，回退客户端需要先降回版本再保留旧表。
