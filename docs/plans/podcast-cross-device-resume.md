# 播客跨设备续听

## 目标

四端都能在另一台设备听过之后正常续听，不需要手动刷新页面，并且不会把别处已经标为已听完的单集改回未听。

现状按当前实现核对如下（`main` 7c5d4b5）：

| | 开播前先读服务器 | 先按旧进度出声再跳 | 已听完会被改回未听 | 切回页面自动更新 |
| --- | --- | --- | --- | --- |
| Web | 是 | 否 | 是 | 否 |
| Android | 是（等待上限 6 秒） | 被 pause 挡住，存在极短漏音，未实测 | 是 | 否 |
| macOS / iOS | 否 | 是 | 是 | 否 |

具体位置：

- 服务器：新会话的非片尾事件一律重算 `completed`，见 `backend/src/wildstring/podcast_progress.py:103-108`。任何端用旧缓存从开头播放都会清掉已听完。
- Android：`frontend/android/app/src/main/java/com/wildstring/app/data/PodcastProgress.kt:91-113` 先读后播。静默改写版本、重传旧位置在 `:155-165`，同一集已在播放器里时不会重新准备（`playback/PlaybackService.kt:278-282`）。节目页「继续」读缓存（`ui/PodcastScreen.kt:1202-1206`），详情按 `loadedDetails` 缓存（`PodcastBrowser.kt:83-85`），无前台恢复刷新。
- Apple：`frontend/ios/WildStringKit/Sources/CorePlayback/PlaybackService.swift:1543-1587` 先按旧位置加载音频，再在后台读服务器并校正。macOS「继续」挑列表里第一个听了一半的集（`MacPodcasts.swift:491`），续听对话框用页面旧数据（`:108-111`），窗口不刷新。
- Web：`frontend/web/src/player.tsx:588-596` 先读后播；已听完从 0 播并上报，清掉已听完。切回标签页不刷新（`podcasts.tsx` 无 `visibilitychange`）。

## 不碰的边界

- 不改历史提交与已发布标签，不改 `contracts/podcast-progress.md` 之外的进度语义，不做跨设备实时推送或播放中轮询别的设备。
- 不回溯修正已有书签：已停在片尾余量内但未标已听完的旧记录保持原样。
- 片尾余量标已听完的规则已在 PR #148 处理，本方案不改它的阈值与触发事件。两者都会改 `save_progress`，以 #148 先合入为前提。
- 不改导入源、托管曲库与下载文件，只改进度读写和页面刷新。

## 方案

### 1. 服务器按意图保护已听完

`PUT /api/v1/podcasts/episodes/{episode_id}/progress` 增加可选字段 `intent`，取值 `resume` 或 `restart`。

- `resume`：用户点「继续收听」。本次会话的写入不会把已听完改回未听。
- `restart`：用户明确从头播放或标为未听。按现有规则重算。
- 缺省：保持当前行为，老客户端不受影响。

**携带方式**：`intent` 不落库，但客户端要在本次收听的**每一次**写入都带同一个值，包括 `play`、`progress`、`pause`、`seek`、`stop` 和离线补传。只带首个 `play` 不够：后续 `progress` 或 `seek` 会让服务器重算 `completed`，已听完又丢。Android 的检查点存在 `podcast_checkpoints.payload`（`QueueDatabase.kt:23`）这个 JSON 字符串列里，新增 `intent` 字段不需要升 Room 版本；旧记录缺这个字段时按缺省处理，行为与现在一致。

**事件序列语义**（服务器）：

- `intent=resume` 时，未完成→已完成仍然允许：位置真正进到 `ended` 或片尾余量，照样标已听完。
- `intent=resume` 时，已完成→未完成被禁止：任何位置和事件都不清已听完，直到出现一次 `intent=restart` 或缺省 `intent` 的新会话。
- `intent=restart` 只表达这一次会话的意图，不是一次性动作；同一会话后续写入继续以 `restart` 处理。
- 检查点在同一次会话内仍然成立。混用不同 `intent` 的写入，以该次请求的 `intent` 为准。

**发布顺序**：`ProgressWrite` 是 `extra="forbid"`（`backend/src/wildstring/podcast_progress.py:26-27`），新客户端带 `intent` 打到旧服务器会得到 422。因此**先升服务器，再发客户端**。旧客户端配新服务器维持现状。

与 #148 的片尾余量处理汇合在同一处：`resume` 时保留已完成、允许未完成→完成；`restart` 与缺省按现有规则。

### 2. 冲突处理（四端共用规则）

当前 Android 和 Apple 都会在 409 时改写版本、开新会话、重传本机位置：Android `data/PodcastProgress.kt:155-165`，Apple `PlaybackService.swift:1615-1640`（`play`/`seek`/`ended` 和播放中的 `progress` 都会重试）。这会让另一台设备刚写的进度或已听完被覆盖。Web 不会覆盖（`podcast-progress.ts:232-235` 在 409 时置 `conflict` 并停传），但也没有自动接管，靠用户重新开播时选择，且提示文案要求用户必须动作。

**服务器不改规则**。409 的响应体里已经带着 `current.device_id` 和 `current.updated_at`（`ProgressState.updated_at` 映射 `last_listened_at`），足够客户端自行判断，不需要新增「接管」概念或字段。

客户端收到 409 后按下面的顺序判断，**先判历史记录，再判设备和时间**：

1. **是历史待发送记录，不是当前正在播放的会话**：采用 `current` 作为新状态，清掉这条待发送记录，不上报、不显示提示。这条优先于下面所有规则，避免同设备或别的设备的旧离线位置覆盖更新的进度。
2. 是当前会话，且 `current.device_id` 与本机相同：重读版本，只重传当前这一次写入。
3. 是当前会话，且 `current.device_id` 与本机不同：看对方已经安静多久（判定方式见下）。
   - 不到 10 分钟：丢弃这一次写入，显示提示条（同一集只显示一次）。**心跳照常继续**，约 10 秒一次，每次都会 409，这不是新增轮询，只是沿用现有上报节奏；每次 409 同时带回 `current`，等于读到对方的最新状态。
   - 满 10 分钟：判定对方已离开，用 `current.version` 重建会话并写入，接管完成，提示条消失。
4. 「用本机进度」按钮就是跳过时间判断的第 3 步，同样用 `current.version` 重建会话。

**安静时长的判定不能拿两台设备的墙上时钟相减。** 客户端时钟可能有偏差，快 10 分钟就会误判正在播放的设备已离开。做法是：

- 优先用 409 响应自带的 HTTP `Date` 头作为服务器时间基准，与 `current.updated_at` 相减；服务器已经会发这个头，不需要新端点。
- 拿不到 `Date` 时退化为本机锚点：第一次看到某个 `(version, updated_at)` 组合时记下本机单调时钟，之后用单调时钟测这段组合没变过的时长；服务器时间跳变或组合变化就重新锚定。

**接管使用什么 `intent`**：

- 自动接管（第 3 步）和「用本机进度」都用 `resume`。两者都只接管位置，不改变完成状态。不能沿用本机会话的 `restart`：本机可能是很早以前的重播会话，对方后来把它标成已听完，沿用 `restart` 会把这个完成状态清掉。
- 清除完成状态只由明确的「从头播放」和「标为未听」承担，也只有它们产生 `restart`。

补充约束：

- 音频不跳。正在播放的位置保留，本机继续本机播放，只是暂不同步。
- 本机不同步的时长取决于对方：对方一直在播，就一直不同步；对方停止或暂停超过 10 分钟，下一次心跳即接管。10 分钟是「对方最后一次成功写入」之后的等待阈值，不是从本机冲突开始计算的上限。

这是**契约变更**：`contracts/podcast-progress.md` 目前写的是「冲突始终询问」，实际四端都没有询问框（Android 的对话框在 0.8.7 删除，Apple 与 Web 只在开始收听时按模式询问）。新规则是「不覆盖正在收听的设备，其余情况自动或手动接管」，契约与四端实现一起改。

### 3. 冲突提示（四端）

播放途中撞到别的设备时不弹框，用播放器里一条不打扰的提示条：

> 另一台设备更新了这一集的进度。本机进度暂不同步到服务器。

跟一个「用本机进度」按钮。不点就继续播，音频和本机位置都不受影响；自动或手动接管成功后提示条自行消失。

- 只显示一次，同一集同一次冲突不重复。
- 只读期间每次 409 都不再弹第二条。
- 自己设备造成的冲突静默重传，不提示。
- 后台补传撞到冲突不提示，回到前台按当时状态显示。
- 现有文案 `playerPage.podcastUpdatedElsewhere`「另一台设备刚更新了本集，请重新选择接续位置」改成上面这句：现在的措辞暗示用户必须动作，实际不动作也能继续听，且不动作最终会自动接管。
- Android 的进度提示通道目前没有接到界面：`data/PodcastProgress.kt:55-56` 的 `message` 在 `ui/` 里没有收集方，`pod_prog_sync_failed_check_network`、`pod_prog_server_update_required` 都是写了没显示。同批接上，提示条复用这个通道。
- macOS / iOS 没有现成的进度提示位置，新增在播放器一栏，沿用现有播放状态的提示样式。
- Web 已有播放中的 409 提示（`podcast-progress.ts:234` 的 `podcastProgress.conflictNotice`「另一台设备更新了本集进度，本机位置已保留，请选择接续位置」），但措辞要改成同一句，并按第 2 节补自动接管。提示位沿用 `player.tsx:622` 的 `podcastProgressMessage` 与 `podcast-progress-dialog.tsx:16-18`。

### 4. Android

- 用户主动点播（列表、节目页、待播、迷你播放器与锁屏恢复）时，即使同一集已在播放器中，也重新走一次 `prepare()`；后台自动恢复仍不重读。
- `intent` 映射：
  - 节目页、列表、待播、迷你播放器、锁屏恢复的播放：`resume`。
  - 设置的「从头播放」模式、以后新增的明确重播入口：`restart`。
  - 「标为未听」：`restart`，位置 0，事件 `stop`。
  - 自动续播到下一集：`resume`。
- `prepare()` 读到 `completed=true` 时，不再取 0 并上报 `play`。改为：用 GET 结果找下一集，以 `resume` 播放；没有则停在当前集并显示已听完，不建立会话、不上报。
- 下一集选择复用现有规则，不另写一套：待播线继续取待播列表的下一项，节目线用 `data/PodcastQueuePolicy.kt:162` 的 `podcastManualNeighbor` 按当前顺序与「跳过已听」设置取下一集。两条线不互相跳，遵守 `contracts/podcast-queue.md` 第 45 行的边界。
- 优先级：明确的「从头播放」与「标为未听」先于「跳过已听完」。用户点「从头播放」时从 0 开始，不因服务器标记已听完而改播下一集。
- 409 按第 2 节处理。`isActiveSession` 保留，但只作为「当前会话可走时间判断」的条件，不再单独作为重传理由。
- 前台恢复（`ON_START`）时刷新当前节目详情，离上次拉取不到 30 秒不重复拉；保留下拉刷新。
- 「询问接续位置」设置恢复可用：`data/PodcastProgress.kt:36` 的 `EpisodeProgressPrompt` 仍在，只缺展示处。位置高于 0 且模式为「询问」时弹出「继续」与「从头播放」。不再删除该设置项，也不做 `ask → 自动` 的迁移。

### 5. macOS / iOS

- 点「继续」先读这一集进度，再出声，等待上限约 1.5 秒。等待期间用现有缓冲状态，不先按旧位置出声再跳。`bootPodcast` 在开播前完成校正后，启动时的跳位置与「出声后跳一次」一并去掉。
- **已读完的判断只用这次 GET 的结果**，不为了确认状态先 PUT。服务器返回已听完时直接改播下一集，不建立会话、不上报，避免动到会话和最近收听时间。
- `intent` 按会话携带：
  - 「继续」：`resume`，此后本次会话的每次写入都带 `resume`。
  - 「从头播放」：`restart`，仍从 0 开始。
  - 自动续播到下一集：`resume`。
  - 标为未听：`restart`。
- **超时或离线降级**：
  - 读取失败时按本机待发送记录或上次已知位置播放，若本机记录里这一集是已听完，则按已听完处理。
  - 这时仍然建立本地会话：生成新的 `session_id`，记下 `intent`、位置与 `base_version`（读不到服务器时用本机已知的版本或 0），写进待发送记录，但先不上报 `play`。这样本次收听有会话身份，后续写入能进入第 2 节的 409 判断，而不会因为没有会话而永远停在「不补传」。
  - 投递由现有上报节奏驱动：**网络恢复后第一次心跳就尝试上报**，不需要额外的定时器或人工动作。若服务器 409，按第 2 节判断：别的设备活跃就显示提示、丢弃本次写入，心跳继续；对方安静满 10 分钟或用户点「用本机进度」时接管。若首次写入被接受，就按正常同步继续。
  - 服务器已是已听完的处理以**获知完成状态**为前提：降级开始时并不知道服务器状态，第一次心跳写入若被接受就正常同步；若响应显示已听完，并且本机是续听，则停止后续写入、按已听完处理并提示可以改播下一集；本机是明确「从头播放」时按 `restart` 正常写入。
  - 这一状态要落盘：进程被杀、切网或页面关闭后，待发送记录随现有本地持久化恢复，回到前台时沿用同一会话继续尝试。
  - 迟到的读取结果一律丢弃：不进位置、不建会话、不改提示。
- 下一集选择复用现有规则，与 Android 一致：待播线取待播列表下一项，节目线用 `resolvePodcastTransitionItem` 与现有顺序、跳过已听完设置。`contracts/podcast-queue.md` 第 45 行的两条线不互相跳仍然成立。
- 优先级：明确的「从头播放」先于「跳过已听完」。用户点「从头播放」从头播，不因服务器标记已听完改播下一集。
- macOS「继续」改为挑最近听的那一集（有进度的集里 `last_listened_at` 最新的那个），全部听完时停住并显示已听完，不退回第一集。
- 窗口重新成为当前窗口（macOS）或场景回到前台（iOS）时静默重拉当前节目，离上次不到 30 秒不重复拉；保留手动刷新。
- 续听对话框和列表行的时间改用刚读到的进度。

### 6. Web

- 切回标签页（`visibilitychange` 回到可见）时静默重拉当前节目，离上次不到 30 秒不重复拉。
- 服务器已是已听完的单集，点播放视为明确从头播放，带 `intent=restart`；其余播放与续听带 `resume`，本次会话的每次写入都带同一个值。
- 读取失败时与 Apple 相同：按本机待发送记录播放，仍建立本地会话并写进待发送记录，先不上报；回到前台或网络恢复后的第一次心跳就尝试上报，按第 2 节的 409 判断决定丢弃还是接管，不能只看服务器是否已听完。

### 7. 四端控件统一

三样控件统一到四端都有、名字一致：

| 控件 | 状态 | 要做的事 |
| --- | --- | --- |
| 单集「从头播放」 | macOS/iOS 只在续听对话框里；Web 只在对话框里；Android 没有 | 四端都加到单集菜单，不依赖对话框先弹出 |
| 续听模式（自动 / 询问 / 从头） | Web、Android 有（Android 询问是死的）；macOS/iOS 没有 | 四端都有入口，三个值都生效；Android 恢复询问对话框；账号级同步见第 8 节 |
| 标已听 / 未听 | 四端都有：iOS `PodcastsView.swift:239`、macOS `MacPodcasts.swift:777`、Web `podcasts.tsx:1418`、Android `PodcastScreen.kt:1476` | 不改，只统一文案 |

- Android 的询问对话框：`data/PodcastProgress.kt:36` 的 `EpisodeProgressPrompt` 仍在，只是 0.8.7 删了展示处，接回去即可。位置高于 0 且模式为「询问」时显示「继续」与「从头播放」。
- 单集「从头播放」的行为四端一致：位置 0、新会话、`intent=restart`；文件没下载完时按现有单集播放规则处理。
- 标为未听：位置 0、新会话、`intent=restart`、事件 `stop`；标为已听：`ended`，位置取时长。

### 8. 续听模式按账号同步

四端各有本机存储，同一账号在 Mac 上选「询问」、Android 上仍是「自动」，同一集行为不同。改为账号级：

- 后端新增 `podcast_resume_prefs(user_id PRIMARY KEY, resume_mode TEXT, updated_at TEXT)`，`resume_mode` 取值 `auto` / `ask` / `restart`，默认 `auto`；`SCHEMA_VERSION` 由 52 升到 53。
- 端点：`GET /api/v1/podcasts/resume-mode` 返回当前账号的模式。写入分两种操作，都由 `PUT` 承担，靠请求字段区分：
  - 普通修改：请求体不带 `initialize`，直接覆盖已有值。
  - 首次初始化：请求体带 `"initialize": true`，只在没有记录时插入，已有记录时不动。
  - 两种都返回**最终生效的值**。初始化失败（别人已经先写）的一方用响应更新本机缓存，不会停留在错误的值上。
- 四端都从服务器读，本机只做缓存以便离线启动；写入成功后更新本机缓存。
- **刷新时机**：登录成功后、回到前台时、进入设置页时各拉一次；开播时直接用当前缓存，不在开播路径上等网络。
- **首次初始化区分「无记录」与「显式默认值」**：`auto` 是合法选择，不能当作未初始化。服务器用「仅在无记录时插入」的原子操作（`INSERT ... ON CONFLICT DO NOTHING`）完成初始化，客户端把本机现有值作为初始值提交；已有记录时不回写。这样两台设备同时首次登录也只有一个赢，不会互相覆盖用户选择。
- 老客户端不读这个端点，行为不变。

### 9. 文档

## 验收（按 AGENTS.md §3 定级）

整体按 **L3**：改动跨后端与三个前端，共享播放代码和契约都动，交付前跑 `make ci`，并按范围补 `make android-ci`、`make macos-test`、`make ios-test`。后端逻辑变更不属于 L0，单独列为后端验证。

- **后端逻辑与契约**（不属于 L0）：`make test-affected`。测试覆盖完整事件序列，不只是单次 PUT：
  - 新会话 `play` 0 + `resume`：已听完保持。
  - 同会话 `play` 0 → `progress` 10 分钟 → `pause`，全程带 `resume`：已听完保持。
  - `resume` 会话播到片尾余量内 `pause` 或 `ended`：未完成→完成正常发生。
  - 新会话 `restart` 位置 0：已听完清掉；同会话后续 `progress` 继续按 `restart` 处理。
  - 不带 `intent`：行为与现在逐条一致。
  - 与 #148 片尾余量的组合：余量内 `pause` 带 `resume` 时标已听完，带 `restart` 时**也**标已听完。`restart` 只影响「已完成→未完成」，不影响正常播放到片尾时置为已完成。
  - 旧客户端（无 `intent`）配新服务器：维持现状。
- **冲突与接管**：
  - 后端：不改规则，测试 409 响应体带 `device_id`、`updated_at`、`version`，足够客户端判断。
  - Android、Apple、Web 用同一组测试向量：「旧设备持续播放和延迟上传不重新抢占」「同设备的历史记录撞到冲突被清掉而不是重传」「不到 10 分钟丢弃写入」「满 10 分钟用 `current.version` 接管」「历史待发送记录不因超时获得写入权」「点『用本机进度』立即接管」「自动接管使用 `resume`，不会清掉对方的已听完」。
  - 时间基准：注入服务器的 `Date` 头测试「客户端时钟快 10 分钟也不会误判对方已离开」；拿不到 `Date` 时用单调时钟锚点，测试服务器时间跳变会重新锚定。
  - 提示条：出现一次、自动接管后消失、重试不重复弹。
- **Android**：`make test-affected` + `make android-ci`。补「同一集已在播放器里再次点播会重读」「已听完时不建立会话、不上报、改播下一集」「`intent` 各入口映射」「旧 JSON 缺 `intent` 的记录按现有行为重放」「询问模式弹框后选择继续或从头」「进度提示接管到界面」。
- **Apple**：`make macos-test`、`make ios-test`。改现有 `playPodcastEpisodeWithoutExplicitPositionRecoversNewerRemoteProgressOverStaleCache` 为先读后播语义。补「已听完点继续只 GET、不 PUT，改播下一集」「读取超时后建立本地会话、联网后第一次心跳直接 PUT」「迟到读取结果被丢弃」「窗口回归刷新」「续听模式设置读写」「单集从头播放」。
- **Web**：`make test-affected-desktop` + Playwright。补「页面不刷新时先读服务器再出声」「已听完带 `restart`」「读取超时后建立本地会话，回前台或联网后第一次心跳直接 PUT」「单集菜单从头播放」。
- **离线降级的完整链路**（Android、Apple、Web 各一条）：读取超时 → 按本机位置播放并落盘会话 → 联网后第一次 PUT 返回 409 → 对方持续写入时不接管、提示条只显示一次 → 对方停止满 10 分钟后下一次心跳自动接管 → 提示条消失、位置同步为接管时的本机位置。
- **续听模式同步**：后端测默认值、普通覆盖与 `initialize` 只插入、账号隔离、返回最终生效值；四端各测「本机无值时用服务器」「初始化被对方抢先时用响应回写缓存」「离线时用缓存」「登录、回前台、进设置页都会刷新」。
- **视觉与状态**：四端节目页、续听对话框、单集菜单和设置页，覆盖正常、空、加载、错误、权限不足；桌面与 390px 宽度、浅深主题各一次，逐张查看截图。Web 用 CI 上传的 `browser-visual-evidence`，并写明哪些状态没有截到；原生端在本机模拟器渲染。不能只用节目页截图代表全站通过。
- **交互路径**：四端都要走通播放、切页、返回，不能只看截图。
- **真机路径**：Android 与 macOS 同一账号。A 端听到 40 分钟，B 端不刷新点「继续」，确认不先出声、无跳转、位置正确；A 端标已听完，B 端再点「继续」，确认已听完不被清掉并改播下一集；B 端点「从头播放」，确认从 0 开始且已听完被清掉；A 端暂停 10 分钟以上，B 端继续播，确认能自动接管并同步。

## 风险与回滚

- 老客户端不带 `intent`，仍会清掉已听完。服务器只能保护新客户端；彻底解决要等各端升级。不为此做位置启发式，因为「标为未听」同样是新会话从 0 上报，启发式会误伤。
- 发布顺序是硬约束：服务器先升，客户端后发。新客户端先到会让每次进度写入都 422。
- 冲突策略从「询问」改成「不覆盖正在收听的设备，其余自动或手动接管」。只读时长取决于对方：对方持续播放时本机一直不同步，对方停止或暂停满 10 分钟后下一次心跳接管，不设固定上限。以提示条说明，不新增对话框。
- 10 分钟接管窗口是启发式：对方只是暂停超过 10 分钟时，会被本机接管。这与「另一台不再听」同义，接受这个误判。
- 拿不到 HTTP `Date` 时的单调时钟降级只能保证「从本机首次观察到该版本起保持不变满 10 分钟」，实际接管可能比对方最后一次写入晚一些，最长多出一次心跳间隔和一个尚未观察到的间隔。可接受，不为此增加服务器端点。
- 续听模式改存服务器后，首次初始化只在服务器无记录时写入，且用原子插入，两台设备同时首次登录也只有一个赢，不会覆盖显式选择的 `auto`。
- 恢复 Android 询问对话框会改变默认操作路径（原来静默续听）；不需要迁移旧值，因为 `ask` 一直是合法值，只是之前没接上界面。
- Apple 开播前等待最多 1.5 秒，弱网下比现在慢。以缓冲状态提示，超时退回本地位置且不上报，不回退成「先出声再跳」。
- 回滚按提交单元进行：服务器 `intent` 缺省行为不变，客户端可单独回退。Android 的检查点存在 `podcast_checkpoints.payload` 这个 JSON 字符串列里（`QueueDatabase.kt:23`），新增 `intent` 字段不需要升 Room 版本；回退后旧版本会忽略这个字段，不影响已有记录。
